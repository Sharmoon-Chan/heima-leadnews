## 1. 先保护工作区，再动环境

在任何代码、依赖、配置修改前：

- 查当前适用的 AGENTS.md，记录 HEAD、分支、git status、diff --stat；保存 tracked 的 git diff --binary 和未跟踪文件清单。差异文件属于本机证据，先检查是否含敏感配置，含密钥的原件只在本地保管，公开摘要脱敏。
- 备份现有未跟踪业务源文件，尤其 KafkaErrorHandlerConfig.java；补一份改动文件 SHA256。只保存 diff 不足以恢复未跟踪文件。
- 记录已经修改的 gateway/user/JWT、article、search、schedule、wemedia 各文件。不得把这些已有改动当作本阶段新成果。
- 不自动提交全部现有改动，不 stash/reset/clean。建立 V0-workspace 清单，至少包括 HEAD + dirty patch + 未跟踪文件备份 + 文件哈希，可按清单恢复才算版本冻结。
- 后续新任务开始前也要核查 dirty 文件。需要拆提交时明确文件和 diff 块；不得顺手提交历史 JWT 改动。

本卡允许新增 docs/optimization 的运行记录、benchmarks 的环境检查/数据准备/压测脚本和本地配置示例；真实凭证放未跟踪本地配置。不能为“启动方便”直接修复本轮业务缺陷。

## 2. 采集环境清单

记录命令、时间、输出文件和失败退出码，至少包含：

| 类别 | 需要回答的问题 |

| 主机/压测端 | CPU 型号与可用核数、内存、磁盘、OS；压测端是否与服务同机；VM/容器 CPU 和内存限制 |
| JVM/Maven | 实际 java -version、Maven -version、JAVA_HOME 的实际作用、JVM 堆与 GC；记录工具绝对路径 |
| 部署 | 是现成课程 VM、Docker，还是本地进程；不要同时搭两套；列明地址、端口、网络和挂载目录 |
| 组件 | Nacos、MySQL、Redis、Kafka broker、ES、MongoDB、MinIO 的服务端版本、状态、数据目录和配置来源 |
| 应用 | 服务端口、网关路由、实例数、线程池、数据库连接池、Redis 客户端池/超时、Kafka group/ack/分区/并发 |
| 数据 | 数据库表和索引、文章数量/正文大小分布、ES mapping/analyzer/doc_count、Redis 缓存 key 范围 |

Maven 可先尝试已发现的 D:/Soft/apache-maven-3.6.1/bin/mvn.cmd。根 POM 聚合课程演示工程，不盲跑全量测试：核实 article 的依赖后，可用选定模块及依赖的 Maven 命令做 compile；search 分开编译。保留完整命令、JDK 和输出，不能因历史“编译通过”跳过验证。

## 3. 按依赖实际启动，不扩大改造

先确认已有 VM/组件是否可用、是否有可恢复数据，再选择本地可行方案。可以使用现有开发环境，不覆盖全局 Docker/Nacos 配置。需要新增环境时提供版本固定的配置、启动/健康检查/停止步骤和独立数据卷，验证目标目录后才清理测试资源。

优先跑 article 缓存实验所需的真实依赖；article 启动若还加载 Kafka、MinIO 等，按 Bean 和配置补齐，不能凭经验省略。search 的 MongoDB 历史写入、wemedia/schedule 的发布依赖分别列出，避免把无关组件错误归因于缓存性能。

每条最小链路记录“请求 → 应用 → 存储/消息 → 业务结果”：

1. 详情 API：存在 ID 内容正确、不存在 ID 业务码正确；第二次请求是否读缓存需有服务端计数或存储证据。
2. 首页/静态详情：找到前端或调用方真实使用的接口；找不到则明确“未接入核实”，不能把新详情 API 视作实际页面主路径。
3. Kafka/ES：尝试消费者启动及一条合法索引消息，记录成功或具体启动异常。不在本卡偷偷修接线。
4. 搜索：能启动则用合法参数查询一次，记录查询和结果；若因 Kafka 接线等启动失败，将该链路标记为阻塞。

本卡允许 article 基线先通过、search/Kafka 挂起至 P2.0，**不要求为三个链路同时可用而越界改业务代码**。影响所有链路的环境阻塞需解决或交接；不把失败请求压出的高 QPS 记作基线。

## 4. 冻结首份数据与基线

按统一规范选择本机可承受的首档数据，建议先 1 万篇合成文章、固定随机种子、固定文章 ID 清单，保存生成器和 checksum。P0 只需详情小规模样本；ES 数据集可等 P3 再导入，不能为了凑规模拖延环境验收。

数据库记录必须兼容当前业务实体和正文格式。合成数据不能携带真实隐私；插入/删除有明确 ID 范围，不覆盖现有个人数据。测试 key/topic/index 采用可识别命名，若代码硬编码 topic/index 则在独立开发实例运行并写明隔离方式。

选择 1 个已验证接口，先低速冒烟，再以 10/30/60 并发候选档做短时摸底；这些是起始候选，不是最终容量。按规范固定热身、采样、业务断言和资源采集。P0 目的是脚本能跑、数据可信，正式 A/B 重复次数在后续阶段补齐。

现有代码已经含缓存改造，因此将其命名为“V0 当前工作区基线”。本卡不回退课程源码，不补造优化前接口。公平的“直查 DB / 缓存”同接口对照在 P1.0 建立后重新采集。
