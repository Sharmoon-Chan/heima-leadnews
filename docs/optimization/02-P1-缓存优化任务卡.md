### EVID-001 固定补证流程

这是 P1.0 派发后的执行要求，本次仅完善任务说明，不提前发请求或删除缓存。

1. **固定环境和冷 key。** 记录 profile、数据库、Redis DB、精确测试 key、文章 ID、版本和 run_id；使用实际结构的隔离测试数据，包含大于 2^53-1 的 ID。确认目标 key 属于本次测试后，只清除该单个 key 并保存操作结果，不枚举全库或删除课程/他人的 key。记录开始状态、采样窗口和后台任务干扰。
2. **逐次请求，逐次落盘，从文件断言。** 对同一存在 ID 顺序请求两次，再请求一个已知不存在 ID。每次分别保存状态/响应头、原始 body、时间、请求 ID 和目标 URL，再读取这些文件核验：存在文章应 HTTP 200 / 业务码 200、ID 精确匹配、标题/正文正确；不存在应业务码 1002。冷热返回的 ID 类型与 null/缺省规则按 CACHE-006 一致，不能用 JavaScript 浮点数解析 19 位 ID 后再做“相等”判断。任一次业务码 503、错 ID、缺文件或解析失败，都将本轮标为失败并保留原件；成功重跑另建 run_id，不覆盖失败样本。
3. **按请求追踪 SQL，Redis 状态作辅助。** 用请求关联的 SQL/回源计数或可明确归属的 MyBatis/JDBC 日志，分别核对第一次请求和第二次请求的文章/内容查询。当前实现对存在文章的冷读预期是两条 SELECT、热读预期为零，必须由实际记录支持，不能预填结论。若临时启用 general_log，记录原设置、采集范围、关联方法和恢复步骤，仅用于功能补证，不混入正式性能轮次。Redis 对精确 key 记录 EXISTS/PTTL 等状态，存在与 TTL 本身不能证明某次请求命中。

SHOW GLOBAL STATUS 的 Com_select 是全局累计计数，会混入后台/其他连接查询；三次请求后的一个总差值也无法归属到每次请求。可作为辅助观察，在相邻请求间分别采样并记录干扰，但不能单独用它判定“首次两条、第二次零条”。

补证交付至少包含：逐请求原始响应、从落盘文件生成的断言结果、按请求 SQL/回源记录、精确 key 状态、manifest、hash 和复跑命令。正确性、命中证据与响应契约均通过后，才可关闭 EVID-001；同轮的性能收益仍须独立 A/B 验证。

验收：同一组存在/不存在 ID 的返回和断言一致，开关可恢复，快照可定位，原始逐请求结果与 DB 计数可核对。明确简历最终若写详情缓存，必须描述这个 API；没有完成前端接入，就不说整个 APP 详情页都受益。

交付：records/P1.0-交接.md、路由表、实验对照实现说明、首份受控基线和代码差异。完成即停。

P1.0 实施偏差决定：普通配置开关默认 true、无新端点，负责人同意保留，只在实验的 p1 配置使用；不把“仅测试 profile 下使用”说成代码已强制限制。正式性能数值仍须多轮证据。

## P1.2：热点重建与锁生命周期

2026-10-30 派卡补充：实施细则、等待到期的明确失败策略、C1–C7 与冷突发证据要求，以 [P1.2 独立单卡](02b-P1.2-热点重建与锁生命周期任务卡.md) 为准；P1.1a 前置已通过。本节保留目标范围。

执行前先验收 P1.1a：采集器须拒绝旧目录并保留失败；冻结 P1.1 修后 14 项与采集脚本版本，不以新运行替代缺失历史。

**待复现风险：** 当前 3s 锁使用固定值，finally 直接 DEL；未得锁等待 50ms 后直接回源。慢 DB 下可能出现误解锁与回源风暴。

先用可控延迟/屏障复现，再做最小修复：锁值改为每次获取的唯一所有权令牌，释放必须原子比对后删除；未获锁走有总时间预算的缓存重查/退避，超预算按明确策略返回或有界回源。不能无界 sleep，也不能让所有等待者同时直查。

写清保证边界：有租期且不续租的锁，遇到查询超时仍可能有新重建者；所有权释放只防误删，不自动保证全程仅一人回源。若引入限流/信号量，说明是单实例还是跨实例。优先简单可解释方案，不因学习目的升级为完整锁框架。

必做功能试验：正常热点过期；DB 查询超过锁租期；旧持有者结束时新持有者仍存活；持有者崩溃后租期回收；Redis 超时；等待线程中断。设置至少两个并发执行者，允许本机进程实现，无需虚构集群部署。

比较修复前后同一冷 key 突发下的总 DB 查询/峰值并发、请求 P95/P99、错误/拒绝/超时，不能只看平均延迟或锁命中数。配置候选由 P0 和慢查询实测确定，不能为了通过试验无限加长租期。

计数注意：P1.0 的 dbSelect 是按成功路径记录的 DAO 调用数。此阶段要覆盖真实回源尝试、异常退出、同时回源数，不能把完成请求的 0/1/2 标签当成失败/超时场景的全量 SQL 压力证据。

验收：无误删新锁；等待有上界；所有回源和降级均计数；样本内 DB 压力变化有证据；清楚说明租期/超时极端下的剩余风险。

## P1.3：事务提交、延迟删除与一致性窗口

P1.1 补充范围：将服务内 static_url 回写和行为计数更新纳入提交后失效，保留现有响应字段，测高频计数导致的失效/回源放大再讨论取舍。新增分支需用独立测试夹具控制生成 ID，补“预写空值 → 真正新增 → 提交可见”样本；不改生产 ID 算法。外部 SQL 不扩为 Canal，需明确经服务或按 ID 失效，TTL 不能宣称任意并发下的严格陈旧上界。

真实 MinIO/静态化/Kafka 端到端联调放 P2.0 独立卡。本阶段可隔离外部依赖验证对应应用写方法的失效；不得用模拟 UPDATE 冒充真实上传和消息同步成功。

**待复现风险：** 当前类级事务内立即删除并安排 500ms 后再删；方法执行/提交超过窗口时，删除可能都早于提交。不能把“SQL 已执行”当作“事务已提交”。

工作内容：

1. 用屏障明确控制读 DB、写事务提交、删缓存、旧值回填四个时点，首先复现当前实现的竞态。记录读连接隔离级别和是否持有旧快照，不能用普通压测偶然没出错代替证明。
2. 将针对已提交数据的失效安排在成功提交后执行；回滚不应按成功变更发布。核查详情只读方法是否需要继承类级长事务，防止重试仍读旧快照和等待期占住 DB 连接。
3. 保留先更库、提交后失效与延迟二次失效的方案，覆盖新增空值占位和实际更新入口。没有事务时如何触发、afterCommit 回调失败如何记录都需说明。
4. 管理延迟任务线程的生命周期和待执行任务指标，记录进程重启、删除失败、队列积压的处理与 TTL 兜底。单机线程池能被接受，但局限必须留档；不在此卡扩为分布式延迟平台。
5. 选取基于回源耗时与调度抖动的有限延迟候选，参考 200/500/1000ms 只是试验起点。固定其他参数做受控竞态和读写混合试验，记录实际执行时间，选择有依据的窗口。

不要把 500ms 解释为“按主从复制延迟调优”，除非真的部署了主从并测过。延迟双删没有覆盖任意长回源和进程故障，实测最长陈旧窗口也不是理论上界。

验收：受控的提交前回填、提交后回填、事务回滚、补录、延迟执行失败场景各有结果；窗口内/窗口外的可见性与声明一致；至少一次同负载前后对照，正确性先于吞吐。

交付：records/P1.3-交接.md、CACHE-RACE 报告、参数选择及淘汰理由、剩余风险；P1 汇总指向每个子任务 run_id。完成后等待 P1 总验收，不进入 P2。
