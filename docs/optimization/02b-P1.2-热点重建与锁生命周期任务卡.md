## 等待与失败策略先固定

本卡采用简单的保库策略：等待预算耗尽或 Redis 读取/争锁不可用时，**不让所有等待者无锁回源**；沿用既有业务码 SERVER_ERROR(503) 返回明确失败，并在结构化结果区分 wait_budget_exhausted、redis_error、interrupted。不新增成功兜底、不把它们算作正常命中。不修改已有成功/不存在响应结构，不新增枚举以扩大范围。

先记录 3000ms 原租期及修前正常回源耗时，再在修复前冻结有限的等待预算/退避候选。租期初始仍 3000ms 作对照，较短租期仅用于功能故障试验；新增参数须有有限正值及非法配置处理，最终值须给测量依据。本卡不要求宣称这些值已是性能最优。

每次缓存/锁 I/O 前检查期限，Redis 客户端须有明确的有限 I/O 超时。循环预算、单次 I/O 超时、DB/连接池等待、客户端 HTTP 超时分别报告：循环有预算不等于整个 HTTP 严格在该毫秒数内结束。不要用客户端超时掩盖服务端仍在睡眠/回源；确认后台请求收敛后再结束采集。

令牌释放只防旧持有者删除新锁；不续租时仍可能出现多个回源者，过期持有者回填也不是由释放 Lua 自动解决。记录锁失效后的写缓存策略及剩余风险，不宣称租期外严格互斥、故障下线性一致。当前类级事务可能让等待者先占 DB 连接，记录实测影响，P1.3 再拆事务。

## 冷突发对照与计数

在同一只读数据集、锁租期、DB 延迟、日志等级、预算说明和机器资源下，用专用夹具同步发起 C1/C2：初始并发 10、30 各至少 3 对修前/修后（按 AB/BA 交替），每次都新 run_id、精确 key 冷状态。资源不足可在试验前缩小并记录理由；不要沿用未验收的稳态负载脚本伪装同步突发。不为了出 QPS 运行大规模稳态压测。

每个请求有 run_id、process_id、request_id，每次回源有 attempt_id 和 start/end/error 事件。分别记录回源尝试/完成/异常、DAO 调用尝试（在调用前递增）、实际 SQL、当前/峰值回源并发、等待耗时、锁结果/释放结果、正确响应、预期拒绝、其他错误和超时。try/finally 归还并发计数；跨进程用事件区间汇总，不把单 JVM AtomicInteger 当全局峰值。

并发 SQL 用请求/线程/连接标识或受控测试 DAO 归属，不使用相邻 metric 行之间的全部 Preparing；没有独立 SQL 证据的数字标为 DAO 调用/回源尝试。不能只统计成功完成请求中的 dbSelect=2。模拟延迟插在哪一步写清，连接等待与实际 DB 执行分别说明。
