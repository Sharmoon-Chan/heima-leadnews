## 只处理一个主要问题

现状：ApArticleServiceImpl 类级 @Transactional 覆盖 getArticleDetail。缓存命中、等待争锁也可能先占连接/保留事务；saveArticle 事务内立即删缓存，500ms 后再删，若提交更晚，两次失效都可能只清掉提交前的旧缓存。

本卡只做：读路径不跨缓存等待持有长事务；既有 saveArticle 新增/更新分支请求的失效在真正成功提交后执行，回滚不触发成功失效。若详情的文章/正文两次读取需要同一快照，使用短的 DB 读取事务，结束后再回填缓存；需要通过实际 Spring 代理生效，不能用 private/self-invocation 注解冒充独立事务。

缓存响应字段/字符串 ID、正常/空值 TTL、P1.2 UUID/Lua/3000ms 租期/1000ms 等待预算及退避策略不改。500ms 暂保留原值，只是现有候选，不开始选参。不修改 JWT、mapping、依赖/pom、课程库、外部直写同步或 MQ 协议。

## 必须验证的六组场景

| 场景 | 必须证明什么 |
|---|---|
| T1 长事务内两删均早于提交 | 修前真实失败；修后失效的起点在 COMMIT 成功之后，提交后新读可见 V1。记录 UPDATE/COMMIT/DELETE/回填的关联时序及读连接隔离级别 |
| T2 回滚 | 写方已执行更新并登记失效后，受控回滚；DB仍V0，成功提交回调/延迟删除未执行；不能只说返回错误就证明回滚 |
| T3 提交后旧读回填 | 让一个提交前读到V0的读方，在提交后即时删除之后回填；固定500ms第二次删除能覆盖的窗口给一条成功样本；再给超出窗口的剩余风险样本，不承诺任意长回填都被覆盖 |
| T4 有/无事务调用 | 保存实际事务状态与回调次数；无事务分支立即失效并按现有策略安排第二次，不能依赖一个永远不触发的回调。通过真实代理调用证明注解生效 |
| T5 提交后 Redis 删除失败 | 只对本轮实例/精确key注入，MySQL真实提交保留；异常记录与失败计数可查，不能把已提交写入伪装成回滚。即时删除失败也要明确第二次是否安排及其结果，不要求建设可靠分布式补偿平台 |
| T6 读路径连接与契约 | 缓存命中/锁等待的事务状态及连接占用有证据；详情冷读两查询的短事务/快照范围明确。验证大ID字符串、冷热/不存在及正常等待最小回归，保留P1.2失败策略 |

T1/T2/T3 的 DB 提交必须是真实 MySQL 事务；模拟 DAO、手写一个“commit”事件或直接 SQL UPDATE 不能代替实际应用方法/事务代理。允许测试专用屏障/连接拦截器，冻结它与业务基线；延迟只在本轮实例、精确测试 ID 生效，默认关闭，无新线上控制端点。

事件包含 run_id、pid、request_id、事务/连接标识、articleId、版本、时间戳与阶段。以事务管理器实际 afterCommit/afterCompletion 或可关联连接证据标明提交结果，跨线程分别关联；不把客户端返回时刻当 COMMIT 时刻，不把相邻日志之间所有 SQL 归给并发请求。
