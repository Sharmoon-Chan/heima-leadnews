## 起点与本卡问题

当前 DetailCacheInvalidator 使用一个 daemon 单线程 ScheduledExecutorService；没有明确的 Bean 销毁逻辑，延迟队列仍无界，只有累计成功/失败数。second_delete_scheduled 在调用 schedule 前增加，拒绝也可能进入“已安排”数。旧成本脚本将 second_begin 当 executed，不能据此确认 Redis 删除完成。

P1.3b 已验证写提交后失效及回滚；本卡沿用这些行为。先解决任务状态和关闭可解释性，队列有界策略、500ms 外旧回填和延迟候选比较留后卡，不宣称本卡解决了任意并发一致性或崩溃补偿。

## 允许改动与工程约束

- 500ms 与单线程保持。优雅关闭等待可以新增一项工程配置，在运行前冻结测试值和单位；不称为压测选出的参数。保持原第一删及失败不反向回滚已提交业务的语义。
- 排队/运行/终态对象只保留当前活跃任务，结束释放引用；累计统计不会使每个已结束任务永远留在内存中。

## 三项实现要求

**1. 区分提交、入队与完成。** 只在成功接受后计 accepted，拒绝单列并带原因。为每个第二删提供进程范围唯一 task_id，串起 accepted/start/succeeded/failed/cancelled/rejected 和文章/来源/时间。成功仅在实际 delete 返回后记录；开始不能升级为完成，失败和取消也不能算成功。

在已静止的检查点核对 `accepted = queued + running + succeeded + failed + cancelled`、`submit_attempts = accepted + rejected`；说明累计计数/当前数量以及取消口径。拒绝或取消后不遗留虚假的 pending，状态与日志不能重复进入终态。原 stats 字段保留兼容，必要新字段明确单位。

**2. 真正管理 Bean 关闭。** 用真实 Spring 生命周期钩子关闭本组件拥有的调度器。关闭开始后新第二删提交要明确拒绝；有界等待到期时处理未执行任务、计取消并释放资源。记录关闭起止、等待耗时、queued/running/终态、是否终止。只能操作自己创建的调度器和线程；不关闭共享 Redis/DataSource 或别的线程池。

运行中 I/O 可能比等待窗口长；记录实际剩余和后续终态，不能在 close 返回时强写“全部完成”。本卡不引入持久化补偿或用优雅关闭冒充 SIGKILL/机器崩溃。

**3. 默认关闭的受控装配。** 停顿/失败只对本轮精确 ID 的第二删生效，第一删不受注入影响。保留真实执行器与实际关闭钩子；允许替换 Redis 出口来精确观察状态，但声明它是离线协作者，不能把 mock 整个调度器的结果当真实排队/关闭证据。新实验组件仍缺省/false 不注册，true 才出现。

### A：原子协调接受/发布、运行、关闭与终态

- 当前schedule先使任务可见于执行器，成功返回后才accepted++/activeTasks.put，没有和destroy同步。500ms不能保证提交线程及时继续，不能靠延长睡眠修正。
- 负责人用真实ScheduledThreadPoolExecutor的返回门控和真实Context.close复现：关闭已结束且future已取消，提交继续后accepted=1/queued=1/active=1/cancelled=0；另一个任务真实成功后再发布，accepted=succeeded=1、queued=running=0、active=1。后者把终态对象重新放回活跃表。
- 使用一致的同步/发布协议保证成功接受后任务登记、事件及开始执行之间的顺序；accepted仍只在成功返回后计数，拒绝不能算接受。关闭不能遗漏尚在提交交接中的已入队任务，终态移除后不能再写回活跃表。
- QUEUED检查及RUNNING写入要与取消/finish原子协调；当前volatile检查再赋值没有和终态用同一保护。已取消任务不复活，不重复终态或计数；关闭后拒绝、运行中超时回执等原语义保持。
