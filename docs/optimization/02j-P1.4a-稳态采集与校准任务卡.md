## 3. 采集器必须形成的证据

旧 [p0-detail-load.ps1](../../benchmarks/load/p0-detail-load.ps1)是闭环 smoke：线程随机种子不固定，请求行留在内存到尾部、完整正文未留存，资源按最近 java 进程选择。本卡新增有明确身份的入口，不直接把旧成绩升级为正式证据。

1. **流量计划和上限。** 使用固定到达速率，记录 offered、started、completed、in-flight 与 dropped。客户端在途上限初始 16，请求超时 5 秒；上限满时明确记录 dropped 的计划槽位，不积压无限队列、不暗中重试或补发。每个采样槽位有唯一 ID；正常完成时满足 `offered=started+dropped`，排空后 `started=completed`。受控中断则保留 pending 集及前缀，不伪造完成。
2. **完整原件和断言。** 每个已完成 HTTP 响应保存状态、头、原始正文 bytes、长度、SHA256、关联 request_id、目标 ID、URL 和阶段。正文中包含换行/逗号仍可无损读取。只有 HTTP200、业务200、字符串 ID 精确匹配且文章字段/正文符合真值才算本场景正确；200 包着 503、错 ID/字段、非法 JSON 分别失败。完整非 200 响应也保留正文；传输异常无法取得完整正文时明确注明，不补造 body/bytes。
3. **完成后持续保存。** 在采集循环中持续写出已完成响应与账本，避免全量放在内存到尾部。起始计划、实际 dispatch、客户端完整响应观察、持久化标记分开；客户端延迟与调度等待分别报告，不拿写盘时刻充当网络完成。记录 Flush 策略和已持久化前缀；用有限中断验证已 Flush 记录仍可读，未完成请求不补造终态。若采用批量 Flush，公开间隔及可能丢失的未 Flush 尾段，不能宣称逐条已经持久化。
4. **服务端计数归属。** 用 run_id/request_id 和采样阶段关联实际 cache_hit/miss、回源及 DAO/SQL 记录。回源请求、DAO 调用与物理 SQL 分开；只有 DAO 证据时如实标注，不能换名为 SQL。允许单独少量顺序功能请求核对物理 SQL，详细 SQL 日志不混入校准。客户端响应、服务端记录与未匹配项全部对账，不能只取某段全局计数差值。
5. **资源和日志。** 从本卡实例 manifest 获取确切 Java PID，固定间隔 1 秒记录服务/采集进程 CPU 与内存、线程，并保存堆/GC/连接池的可用观测。不能用「最近 java」代替本次 PID； unavailable 项有原因。A/B 使用相同日志和探针等级，记录采集/打点 I/O 开销，确认没有逐篇正文日志；不要为关日志修改生产代码。
6. **从原件汇总。** 所有响应、正确响应的 P50/P95/P99 分别计算，失败和超时单列；分位数用排序后 nearest-rank，并记录定义。采样窗口内完成速率与窗口后排空结果分别报告，不能用配置时长掩盖尾部；不得将低错误观测解释为最高容量。原件计数、bytes/hash、错误分类、计划与 summary 必须能独立复算。
