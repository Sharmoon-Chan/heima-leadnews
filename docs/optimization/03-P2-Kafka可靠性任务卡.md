目标是故障可见、有限重试、失败消息有可核对去向；不是为了让 QPS 必须变高。

工作内容：

- 明确空白、非法 JSON、缺 articleId、业务不可重试与 ES 暂时故障的分类。预期坏消息保留隔离证据，不把直接 return 的消息假报成成功建索引。
- 暂时保留当前 1000ms 间隔/3 次重试作为起始配置；确认 3 次指首次失败后的重试，而非总尝试次数。通过失败日志/尝试 header 或可用监听钩子计数，不依赖 sleep 估计。
- 创建并核实 DLT 的分区与序列化配置，保存源 topic/partition/offset、事件 ID、原始消息和异常元数据。
- 专门验证 DLT topic 不可用、分区不存在、broker 发送超时。核实本版本 recoverer 是否等待 send 结果、是否向容器传播失败；需要时使用版本支持的确认式恢复封装，明确超时预算。不能引用新版方法或相信旧注释。
- 准备按事件 ID 选择、确认目标和限速的人工重放脚本。仅重放指定 DLT 测试样本，保留原 ID、attempt/重放记录与重复重放结果，不做全 topic 自动回放。

故障用例：ES 第一次/前几次失败后恢复；持续失败最终进入 DLT；DLT 发布失败；消费前后重启；坏消息后跟正常消息；故障解除后重放。对每个成功发送的逻辑事件给出最终分类和证据。

验收：观察次数符合配置；DLT 成功有 broker 证据；发布 DLT 失败不能被静默当成已恢复；正常后续消息能够继续或明确记录同分区阻塞代价；重放后目标内容正确。没有完整事务性方案时不宣称零丢失和全链路 Exactly Once。

## P2.2：业务事件 ID 与 Redis 判重

状态（2026-11-08）：用户明确要求P2.1另开子agent验收后继续下一卡；[P2.1独立验收](records/20261108-P2.1-独立子agent验收.md)通过后已实施本节。版本化事件、旧消息兼容、ES成功后Redis标记与失败降级已完成，生产5项/消费22项测试及有限真实场景检查通过；另一位未参与实现的子agent已给出[P2.2独立验收通过](records/20261108-P2.2-独立子agent验收.md)。本次停在[P2.2交接](records/P2.2-交接.md)，不继续P2.3。

本卡对应原简历的“业务唯一键 + Redis 判重”，默认需要实际开发。若最终评估认为额外成本大于收益，可以由负责人删除简历该短语并记录决策，不能用 ES 同 ID 覆盖冒充已经实现 Redis 判重。

最小方案约束：

1. 生产端为一次逻辑变更产生稳定 eventId，重发/重试/死信重放复用它；同文章下一次变更产生新 eventId。明确事件格式版本、articleId、发生时间、payload；若有可靠单调 contentVersion 则使用，不能用随机 UUID 充当版本顺序。
2. 兼容现有原始 SearchArticleVo 消息，给出迁移策略和“旧消息没有 eventId 时如何处理”。生产端与消费端格式更改同轮验证；消息 key 使用文章 ID 时要验证分区内顺序，不能据此推断跨重放的全局顺序。
3. Redis 只记录**ES 副作用已成功**的事件标记，marker 含明确 TTL 和命名空间。不得先 SETNX 标成功再写 ES，否则 ES 失败会被重试永久跳过。
4. “查标记 → ES 写成功 → 写成功标记”不是原子事务。并发重复、写 ES 后进程崩溃或标记写失败仍可能再次写 ES，因此保留文章 ID 文档覆盖作为重复写兜底，不承诺只执行一次。
5. Redis 不可用的降级语义需预先写明并验证。优先保证合法事件仍能经 ES 幂等路径处理，允许去重收益下降，并记录故障计数。不能把 Redis 写 marker 失败误报成索引未写，也不能丢弃原消息。
6. 去重只拦截同一事件，不能只用 articleId 作为永久去重键。专测同文章新版本、旧消息重放覆盖新内容的风险；如果未实现版本保护，就明确标“无法保证乱序时最后版本正确”，不能把幂等扩成乱序安全。

场景：无重复；指定重复率；并发同 eventId；相同文章不同 eventId；marker TTL 到期；ES 成功后、写 marker 前崩溃；Redis 读写失败；DLT 重放。若要声称防止旧版本覆盖，须再增加可验证的单调版本保护并做反序用例。

验收：同逻辑事件拦截计数可核对；新事件不会被误判；幂等兜底和剩余窗口说得清；性能结果同时报告 Redis 成本及 ES 实际写次数。不能仅用 doc_count 不变证明避免了重复写。

交付：records/P2.2-交接.md、消息协议、marker 参数依据、MQ-DUP 报告、崩溃窗口和乱序边界记录。完成即停。

## P2.3：消费吞吐、积压与恢复

在已通过的可靠性实现上做实验；若目标是验证异步收益，必须选择等价语义。当前 HTTP 很多步骤原本已异步，不能拿删掉业务步骤的 HTTP 与完整同步流程比较。

每次只调一个变量：消费者 concurrency（候选 1/2/4，受分区数限制）、输入速率、批量拉取或相关超时。先固定分区数；要改变分区数时另建等价测试组，不与 concurrency 同时变化。重试间隔 500/1000/2000ms 可作故障恢复候选，但不能通过取消失败处理提高吞吐。

先无故障稳定输入，再短时超出消费能力形成可控积压，解除故障/停止额外输入后观察追平。记录有效逻辑事件吞吐、实际投递吞吐、重试流量、ES 写入、CPU、lag、最长延迟、恢复时间和失败终态。

验收：选定参数能解释为何有效及瓶颈所在；健康吞吐和故障恢复分别报告；至少 3 轮对照；所有测试事件终态对账完成或明确列出未决。单 broker/单实例实验不能外推生产可用性。

交付：records/P2.3-交接.md、参数对照表、lag/资源曲线和本阶段可认领结论。等待负责人 P2 总验收，不进入 P3。
