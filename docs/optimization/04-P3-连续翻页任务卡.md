## P3.0：mapping、数据真值与真实旧路径

核实 app_info_article 的 mapping、分片、副本、字段类型、doc_values、分词器和 refresh 配置。读取当前 REST 参数、DTO 和调用方翻页方式，确认 minBehotTime 的初始值、边界和精度；保留实际行为，不先改写成大 offset。

建立固定种子的数据集，包含：普通时间分布、超过一页的同一 publishTime 记录、标题/正文分别命中、无命中、最后一页不足一页，以及业务 Long ID 超过 JavaScript 安全整数的样本。建立独立于被测分页逻辑的排序 ID 真值清单。

按实际旧路径连续翻页，核对重复/遗漏及高亮，记录同时间数据被严格时间条件排除的现象或反例。首屏搜索历史写入 MongoDB 的开销需固定：所有组同样开启并记录，或在独立实验 profile 中一致关闭；不能只给新实现关掉。

验收：mapping 和种子可复现；旧路径真实结果与真值能对比；没有把错误返回、漏记录和空页当成性能提升。若旧路径已经足够快，可将后续目标重点放在排序完整性和深度稳定性。

交付：records/P3.0-交接.md、mapping/settings、数据生成器、ID 真值、旧路径功能报告。完成即停。

## P3.1：排序元组、游标协议和兼容

方案方向：publishTime DESC + 唯一业务文章 ID DESC，使用可排序且有 doc_values 的字段。先查现有 id mapping：若是 long 且满足条件可复用；否则为测试索引增加明确字段和迁移步骤。不要直接用 _id 排序，也不依赖隐含的 Lucene 文档顺序。

请求首屏无 cursor，后续页传上一页最后一条**实际返回记录**的完整排序元组，并在服务端调用 searchAfter。前置查询条件和排序保持一致。若采用 size+1 探测 hasMore，cursor 仍取最后一条返回记录，不能取额外探测记录。

接口设计需写成协议说明：items、nextCursor、hasMore，或兼容现有 ResponseResult 的等价结构；pageSize 有默认值及上限，空结果、末页、坏 cursor、关键词改变、排序改变的行为明确。优先兼容现有调用方，若必须新版本入口，在独立协议说明中列迁移与回退。

cursor 至少关联协议版本、查询条件指纹、固定首屏边界和排序值；校验类型、长度和查询匹配。不能让每一页的“当前时间上界”变化而悄悄改变查询。Long ID 若经前端必须以字符串或不透明 token 保真，后端转为 mapping 所需精确类型；测试不能只用小整数 ID。

在冻结索引上逐页遍历，同真值清单做集合、顺序、总数核对；固定页大小或变更页大小按协议验证。同时间文章大于页大小、空页、高亮无片段、无效参数均需覆盖。缺失时间字段、空排序字段的策略也需明确。

当前 7.2 文档下 search_after 面对动态索引会受更新/删除影响。不要默认套用新版 PIT 方案；若实际服务端另有版本，先核实 API 支持和客户端兼容，另行记录决策。至少做一次翻页中插入/更新/删除观察并如实说明非快照边界，不宣称所有动态场景绝不重漏。

验收：冻结数据集遍历无重无漏，严格排序正确；cursor 精度和查询条件绑定正确；接口兼容策略有验证；动态写入边界记录清楚。

交付：records/P3.1-交接.md、游标协议、mapping/迁移说明、正确性用例与 ID 对账。完成即停。

## P3.2：三组对照与参数选择

| 组 | 来源与目的 | 可以得出的结论 |
|---|---|---|
| E0 | 真实旧代码：时间范围 + from(0) + 时间排序 | 真实旧行为、同时间边界和相同负载表现 |
| E1 | 专为实验建立的 from/size 实现，排序与新实现一致 | 与大偏移量方案的机制/开销对比；不得声称它曾是项目真实旧版 |
| E2 | 新 search_after 实现，完整排序元组 | 连续翻页正确性、每页成本、累计成本和资源变化 |

E0 若缺少唯一排序导致结果集合不同，性能可以报告但必须附正确性差异，不能把该差值算成等价语义优化比例。E1/E2 的 query、sort、pageSize、高亮、返回字段、track_total_hits 与数据集完全一致。

建议先用 10 万文章和足够宽的匹配查询，按资源再扩至 100 万；页大小可选 10/20/50，固定后比较第 1/10/100/400 页等深度，确保 from+size 不越过该索引实际窗口。每个页大小对应的可比较深度单独计算。

分别测“游标已经存在时的下一页请求”与“从首屏到目标页的累计请求/耗时”；前者排除游标准备的成本必须在表中说明。超过 result window 的 E1 记录拒绝/失败，不能用错误请求的耗时参加成功请求延迟计算。需要额外扩大窗口的实验只在独立测试索引运行，并记录变更与资源开销。

固定负载等级做至少三轮，记录客户端 P95/P99、ES took、成功吞吐、堆/GC 和精确分页断言。P95 相近也可如实写“同时间记录翻页完整性改善，性能未见稳定提升”。参数选择同时看用户页大小、请求次数和累计耗时，不能只选最好看的单页曲线。

验收：三组来源标识清楚；深度/匹配数/窗口合法；静态正确性通过；请求级与累计成本都有证据；差异超过或落入波动范围有明确结论。

交付：records/P3.2-交接.md、三组报告、数据/mapping/脚本校验、分页和参数总结。等待 P3 总验收，再派 P4。

版本参考：[Elasticsearch 7.2 Search After](https://www.elastic.co/guide/en/elasticsearch/reference/7.2/search-request-search-after.html)。方案边界以实际部署版本及运行验证为准。
