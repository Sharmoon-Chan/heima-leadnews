# 压测与证据规范

所有数值分成“实验候选”“验收约束”和“实测结果”。本文件中的数据规模、并发、时长和阈值都是初始实验安排，没有任何一项是现有性能成绩。P0 记录硬件后可缩小，但需在运行前冻结并说明理由。

## 1. 每次运行的身份

run_id 示例：20261028-P1-2-CACHE-COLD-B-r01，记录本地时区与 UTC 时间。每次运行必须有独立目录、代码标识、配置和数据标识，不覆盖上一轮结果。

正式对照组以共同的源码快照和配置开关切换为优先；必须增加对照实现时，标注“实验对照实现”，不能说它是历史真实版本。环境修复、公共打点和数据准备要同时作用于 A/B。任何一个共同部分改变都生成新 baseline_id，重新采集受影响的基线。

每份 manifest 至少包含：stage、run_id、baseline_id、HEAD、dirty patch hash、未跟踪文件 hash 清单、配置 hash、数据集 ID/种子/hash、机器/VM/容器配额、JVM 参数、组件实测版本、路由、负载模型、脚本版本、预热与采样时间、目标速率/并发、超时、错误判定、隔离资源、开始结束时间。

## 2. 负载与统计方法

- 主工具默认 JMeter 非 GUI，若本机没有合适运行时，可选已验证的工具；P0 冻结工具和版本后整轮沿用。需要安装新 JDK/插件时先查该工具官方兼容要求，不更改项目 JDK 来迁就工具。
- 并发档用于摸底：10、30、60、100 线程逐档增加；正式比较优先固定到达速率，分别记录 offered、started、completed 和 dropped 请求。闭环固定并发的吞吐只是该模型下的观测值。
- 从低负载逐档升压，超过资源或错误停止线即停止当前档；不以无限增大线程数制造更好数字。同机压测记录压测端 CPU，压测端饱和的轮次作废。
- 正式 A/B 的参考安排：热身 60 秒，稳定采样 180 秒，每组至少 3 轮，按 AB/BA 交替顺序，使用相同请求集和独立等价状态。明显长尾或 GC 周期较长时加长采样并留档。
- 冷 key 突发实验采用“预置 → 确认过期/仅删测试 key → 同步突发 → 收集结果”的小试验，至少 3 次；报告每次 DB 回源数、错误和耗时分布，不强套稳态 QPS。
- 同时记录 P50/P95/P99、成功数/失败数/超时数、正确业务结果比例、成功 QPS、资源曲线和最大值。慢请求和失败请求不能从统计中悄悄删掉；若延迟只统计成功请求需明确标注。
- 每轮分别算分位数，再比较各轮的中位数和范围；不平均 P95/P99。不得把客户端延迟与 ES took 混合，took 只作内部辅助指标。
- 优化差值小于重复试验波动时，结论写“未观察到稳定收益”。不要挑最好一轮写简历。

容量搜索前冻结“错误率上限 + 业务正确性 + 延迟 SLO”。起始建议业务正确率 100%、非预期错误率不高于 1%；绝对 P95 SLO 应在 P0 摸底后、正式升压前按业务目标设定。容量只能表述为“在该 SLO 和资源下测到的最高通过档”，不外推成生产容量。

已知不存在 ID 的预期业务响应是该场景的正确结果，但单列计数；超时、反序列化失败、空白页和错误 ID 不是成功。分页 correctness 目标是在冻结数据集遍历中无重无漏；Kafka correctness 目标是注入样本最终去向可解释，均不能仅靠 HTTP 状态判定。

## 3. 数据集与场景

| 实验 | 建议首档和扩展 | 固定内容 | 主要指标 |
|---|---|---|---|
| CACHE-HOT | 1 万文章；按资源扩至 10 万 | 文章正文大小、热门 ID 集；固定均匀或偏热点分布及随机种子 | 正确响应 QPS、P95/P99、命中率、DB 回源次数 |
| CACHE-NULL | 固定 100 个不存在 ID；与大量随机不存在 ID 分开 | 相同 ID 反复请求才是空值缓存主证据 | 每请求 DB 查询数、空值命中、错误分类 |
| CACHE-COLD | 同一热 key 集中过期，叠加受控慢 DB | 并发、DB 延时、锁租期、等待预算 | 峰值回源并发、DB 查询数、等待/拒绝/超时 |
| CACHE-RACE | 同一文章并发读写，加入受控屏障/延迟 | 事务提交时刻、读快照、版本号/内容 hash | 陈旧读数、最长观测陈旧窗口、删除实际时间 |
| MQ-DUP | 固定新事件 + 重复事件；可用 0/10/50% 重复率候选 | 实际消息字节数、eventId、重复抽样规则 | 逻辑事件数、投递数、重复拦截数、ES 实际写次数 |
| MQ-FAULT | ES 短时失败、持续失败、DLT 失败、消费进程重启 | 每轮故障时点、持续时间、消息 ID 真值 | 尝试次数、终态去向、lag、恢复用时 |
| SEARCH | 先 1 万连通验证，正式 10 万；资源允许再 100 万 | mapping、分片副本、正文大小、关键词命中数、同时间记录集 | 分页集合、端到端 P95/P99、took、堆/GC |

ES 的“文章总数”与“查询命中数”同时报告。深分页查询必须实际命中足够多记录；数据总数很大、关键词只命中十条不能用于证明深分页收益。冻结索引后等待预定刷新和健康状态再测；不同分片、analyzer、refresh_interval 或副本数是不同实验。

## 4. 各链路必须采集的证据

| 链路 | 最少证据 |
|---|---|
| HTTP | 请求计划、原始逐请求结果、业务断言、HTTP/业务错误、目标与实收速率、并发和超时 |
| JVM/主机 | 每秒或固定间隔 CPU、内存、堆、GC、线程；采样周期写入 manifest |
| 缓存/DB | 场景级 cache_hit/null_hit/miss、实际 SQL/回源计数、连接池占用；Redis 全局命中率只作辅助 |
| Kafka | producer send 成功/失败、topic/partition/offset、group、尝试数、唯一逻辑事件、ES 成功、DLT 成功、未决事件、lag 时间序列 |
| ES | mapping/settings、doc_count、查询 JSON、每次 hits ID/sort、took、资源与 GC；索引 ID 相同不能证明没有重复写 |

优先复用可用的 Actuator/Micrometer 或轻量计数和结构化日志，不要求先搭完整监控平台。正式性能运行关闭逐正文日志，A/B 采用相同打点等级；排障详细日志在单独功能试验采集，避免日志 I/O 扭曲性能。

## 5. 计算口径

    延迟下降比例 = (A 的轮次中位 P95 - B 的轮次中位 P95) / A 的轮次中位 P95
    吞吐提升比例 = (B 的成功 QPS - A 的成功 QPS) / A 的成功 QPS
    DB 回源下降比例 = 1 - B 的单位请求 DB 回源数 / A 的单位请求 DB 回源数
    重复拦截率 = 被识别并跳过的重复投递数 / 应识别的重复投递数
    缓存命中率 = 正常命中数 / 全部详情读请求数（空值命中另列）
    消费恢复时间 = 故障解除时间到测试消息全部进入确认终态且本轮积压清零的时间

基数为零时不计算百分比。Kafka lag 是 broker offset 与 committed offset 的差，不直接等于逻辑未处理事件数；重试、批量提交和重复投递会影响对应关系。每次最终对账按唯一 eventId 分类：ES 已处理、DLT 待处理、终态拒绝/隔离、未决；这些分类应与发送成功的逻辑事件集核对，不把重试和 DLT 重复计成新事件。

## 6. ES 公平比较的额外约束

必须分成两种计时：已知游标后读取下一页的单请求耗时；从第 1 页连续走到第 N 页的累计耗时/请求数。提前拿到 search_after 游标不能当作“任意跳页”；游标生成耗时是否排除须明示。

同一组对照固定 query、排序、pageSize、高亮、字段返回、track_total_hits、连接池和缓存热身。from/size 的安全深度以内做成对比较；越过默认 result window 的失败另作能力边界记录。若为实验调高窗口，限独立测试索引、A/B 记录共同设置，保留资源风险与原默认结果，不在业务索引上无声修改。

原时间范围游标也参与比较，它已在减少扫描范围，不能假设 search_after 一定比它更快。静态集正确性和动态写入下的观测结果分别报告。

## 7. 归档与有效性

仓库中提交脚本、脱敏配置示例、manifest、摘要和校验值；大体积原始输出放本机 artifacts，交接记录完整绝对路径、大小和 SHA256。不要因为 .gitignore 忽略 logs 或大文件就丢失证据。

跑完先核对请求断言、组间差异、压测端瓶颈、后台任务、数据状态和资源限制；无效轮次保留并写作废原因，补跑受影响的组。最终报告每条结论能追溯到 run_id、原始文件、版本、配置和复跑命令。
