# 留痕、难题与交接模板

规则：先记录当时的假设和观察，再补验证结论；旧记录有误时追加纠正，不抹去原来的失败过程。下面是模板，不是已经完成的工作或已经发生的事故。

## 1. 存放位置与命名

| 内容 | 位置 |
|---|---|
| 本计划、开发日志、问题、阶段交接、决策、报告摘要 | 仓库 docs/optimization/，纳入版本管理 |
| 启动/造数/负载/采集/对账脚本和脱敏配置示例 | 仓库 benchmarks/，各阶段新增 |
| 大体积原始结果、快照、日志、JTL、资源序列 | 本机 D:/Code/Java/heima-leadnews/_optimization-artifacts/{run_id}/ |
| 代码/配置的本地原件和敏感差异 | 本地受控目录；仓库只存脱敏摘要、相对证据映射和校验值 |
| 当前规划时的只读核查证据 | docs/optimization/records/20261028-planning/ |

压测脚本至少接收 baseUrl、数据集、并发/速率、采样时间和输出目录，不把个人 token 或密码写死。每次 run_id 使用独立输出目录，原始证据不覆盖；交接写完整绝对路径和校验值，换机器后补新路径映射。

## 3. 难题/故障卡模板

问题台账放一句话索引，完整卡放 records/issues/{ID}.md。**静态风险、实验复现问题、真实运行故障分开标记。** 一次记录可以后来升级为复现问题，但必须补运行证据。

    ID / 标题 / 阶段 / 状态：
    类型：静态风险 / 实验复现 / 真实运行故障：
    首次观察时间、版本和环境：
    现象：具体错误、延迟、业务数据偏差：
    影响范围与触发条件：
    最短复现命令/步骤、输入和期望结果：
    已验证现象的日志/栈/截图/时序/原始数据：
    初始假设（当时为什么这么想）：
    排查路径：尝试 1 的证据；尝试 2 的证据：
    被排除的原因及依据：
    根因：哪段代码在什么时序违反了哪个假设：
    备选方案与放弃理由（含失败尝试）：
    最终修复与代价：
    修复前后验证（run_id，不能只有“测试通过”）：
    剩余窗口、适用边界、回滚方法：
    个人参与：agent 做了什么、用户亲自复现/分析了什么：
    面试 60–90 秒讲述：背景 → 现象 → 排查 → 根因 → 验证 → 取舍：
    三层追问：为什么原方案失效？新方案何时还会失败？换场景怎么取舍？
    用户能否独立解释：未复述 / 已复述需补充 / 已独立解释（日期）：

没有真实事故也可以讲“本地并发实验发现的问题”。不把 agent 的推断写成个人生产排障经历。用户不必亲手敲每行代码，但需理解最终选择并能够复跑关键实验。

## 4. 决策记录模板

放 records/decisions/{ID}.md；只对重要分歧记录，不为每个小重命名写一篇。

    ID / 日期 / 状态（提议、采用、被后续决策替代）：
    要解决的问题与业务约束：
    已有证据和缺失信息：
    方案 A / B / C：正确性、成本、可观测性、实现和维护代价：
    选择及理由：
    参数来源：默认值 / 实验候选 / 实测选定：
    接受的局限和回滚路径：
    哪些新证据出现时需要重审：
    关联任务、问题、run_id 和代码版本：

建议记录：为何仍接受短暂陈旧；为何未采用 Canal；为何单机延迟任务足够本轮目标；Redis 判重相比纯 ES 幂等的收益/成本；为何 search_after 不提供任意跳页和固定快照。

## 5. 单次实验报告模板

放 records/experiments/{run_id}.md，原始文件位置另列。建议 manifest 使用 JSON/YAML 机器可读文件。

    run_id / stage / 执行时间及时区：
    目的和假设、预设停止线/SLO：
    A/B 组身份：真实历史 / 当前工作区 / 实验对照 / 新实现：
    HEAD + dirty patch hash + untracked hashes：
    机器、JVM、组件版本、资源上限：
    数据 ID、规模、正文大小、分布、seed、checksum：
    配置及脚本版本/hash、接口路由和请求断言：
    开始状态（冷热缓存、索引刷新、积压、后台任务）：
    负载模型、offered/started/completed/dropped、超时：
    热身、稳定采样、轮次与 AB 顺序：
    成功 QPS、业务正确数、HTTP/业务错误、超时：
    P50/P95/P99（注明样本范围）、CPU、堆、GC：
    场景专属指标：DB 回源 / lag 与终态对账 / 分页集合：
    原始结果文件、大小、SHA256：
    观察、波动范围、结论、不能支持的结论：
    有效/作废及理由：
    精确复跑命令、清理/恢复步骤：

参数对照表至少包含：参数名、单位、代码默认、候选集合、固定项、对应 run_id、功能/性能结果、选择值、淘汰理由和局限。只扫描少量有依据候选，不穷举制造工作量。

## 6. 阶段交接模板

文件 records/Px.y-交接.md。交接必须是实际结果，不重复粘贴整个任务卡。

    本次任务/范围/状态：
    前置验收编号、起止版本与既有改动处理：
    完成的业务行为、未完成项：
    新增/修改文件与关键符号：
    编译、功能、并发、故障、性能各自的命令与结果：
    基线及对照是否公平、业务断言是否通过：
    实测指标（无数据就写未测，不填写预期数字）：
    原始证据、manifest、hash 和复跑入口：
    参数变化及证据、失败试验与问题 ID：
    已知局限、回滚与恢复验证：
    建议的下一张卡（不自动进入）：
    需负责人判断的具体分歧：

负责人在交接末尾追加“通过 / 补证 / 退回 / 缩小范围”、原因和日期；通过后更新 README 阶段状态。若只有某链路通过，写明范围，不能笼统勾选整阶段完成。

## 7. 进度规则

只有规划的任务是待派发；执行了但未审是待验收；环境无法运行是阻塞；编译通过不升级成端到端通过；一次压测不升级成稳定性能结论。每次交接后停止，不自动认领后续卡。负责人下一次验收只读取交接、关键 diff 和足够的原始证据，无需重新翻完整聊天记录。
