## 2. 可以接受的功能结论

| 场景 | 原件与日志对应 | 验收范围 |
|---|---|---|
| HOT | reqId 9–12：DB_HIT/HIT/DB_HIT/HIT，DAO 计数 2/0/2/0；到期请求前 PTTL=-2 | 缩短 TTL 下的缓存命中、过期回填和给定样本契约 |
| NULL | reqId 13–16：DB_MISS/NULL_HIT/DB_MISS/NULL_HIT，DAO 1/0/1/0；到期前后状态明确 | 给定不存在 ID 的短 TTL 占位生命周期 |
| JITTER | 12 份响应正确，观测 PTTL 为 19905–28920ms，多个离散设置效果 | 抖动功能生效，不证明分布质量、容量或最终选参 |
| RANDOMNEW | 240 份响应与时间窗对应，DB_MISS=220、NULL_HIT=20、声明 DAO 调用合计 220 | 空值缓存帮助重复 ID，不能阻挡第一次访问的新 ID |
| BACKFILL | 外部插入后仍为 1002；随后带 dto.id 的服务更新清占位并可见新正文；模拟 static_url 更新后缓存仍旧 | 既有更新分支和未失效路径的受控现象，不是新增分支同 ID 端到端证明 |

这些日志的 dbSelect 仍是代码路径的 DAO 调用计数。本轮没有为每个样本单独提供真实 SQL 执行轨迹，不将它写成独立的服务端物理 SQL 计量。

HOT 四个 body 各 1289 字节，NULL 四个各 70 字节；原始哈希比较支持各自一致。示例 ID 仍是 16 位超安全整数，不改称 19 位。

PTTL 是设置后观测的剩余寿命，19905ms 小于 20s 是期间耗时消耗，不是配置生成了低于 20s 的初始 TTL；不能称“PTTL 自身按秒取整”。12 个样本也不足以证明随机分布优良。

## 3. 写入口与三项决定

**服务内 static_url 回写与行为计数更新安排在 P1.3 处理失效。** 保持现有详情响应，优先统一事务提交后的失效语义；计数更新可能频繁，须测失效引起的回源放大，再决定是否需要数据拆分或不同陈旧策略。不能未经测量就把默认 30–35 分钟当作所有字段可接受的窗口。

外部绕过服务的写入不扩为 Canal/全库订阅。要求补录/运维走服务入口或明确执行按 ID 失效；否则只能说明有 TTL 兜底。在“没有旧回源重新写入、没有后续变更”等受控前提下，当前条目到期可重新可见，**不是任意并发情形下最多陈旧一个 TTL 的严格保证**。

新增分支已经加入清理调用，但 b2 有 dto.id、走的是更新分支。CACHE-004 仅部分关闭。P1.3 应用独立测试夹具控制生成 ID，构造“预写空值 → 真正走新增分支 → 提交 → 可见”的样本，不改生产 ID 算法；当前只是未提供该实验，不是理论上无法测试。

**MinIO：允许后续独立联调使用现有真实凭据，不在本轮启用。** 原栈含 InvalidAccessKeyId，支持本轮凭据不匹配的判断。当前 static_url 结论来自模拟 UPDATE，不认领真实 FreeMarker→MinIO→Kafka 成功。真实端到端联调放 P2.0 的独立卡：只改实验 profile，凭据留本地，指定新测试 ID/对象及消息去向和恢复范围，不覆盖课程 dev 配置或静默投递共享资源。本次没有读取或替换凭据、上传文件或发消息。
