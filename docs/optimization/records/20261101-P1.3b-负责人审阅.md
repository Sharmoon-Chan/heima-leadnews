## A：准备脚本的 9/9 没有覆盖真正启动器

`prepare-p13b-run.ps1` 检查生成事件路径的参数，随后生成配置；实际使用的 `start-p1-2-instance.ps1` 只检查路径存在、日志重名和依赖，直接把 `ProbeConfig` 交给 Java，没有读取其 `events.file` 并检查本轮根。配置在 prepare 后被改动，或启动时换一个配置，这道关卡仍可绕过。

负责人将实际配置放在新测试运行根内、`events.file` 指向根外的新封存哨兵，调用**原启动器**，仅把 JavaExe 换成记录型离线程序。结果：**Java 调用 1 次，启动器退出 1，路径保护未拒绝**；哨兵 hash/大小均未变，真实 Java/网络调用 0。退出 1 是替身没有监听端口，不能当作启动前拒绝。

原 9/9 只认可为 prepare 参数保护；TOOL-003 的实际启动关卡重新打开。补修须让实际启动入口读取实际配置，在任何编译/Java/外部回调之前拒绝越界，并记录有效调用计数。

## B：static_url 更新 0 行仍被当作成功写入

ArticleFreemarkerServiceImpl 忽略 `apArticleService.update(...)` 的 boolean 结果，随后无条件记录 `static_url.updated`、调用 `invalidateAfterWrite`。原卡已明确要求“0 行更新不伪报成功失效”。

对实际 POST class 的离线方法契约反例，DAO 返回 false：**UPDATE 调用 1、updated 事件 1、失效登记调用 1、Kafka 记录调用 1**。返回 true 的正向控制也为登记 1。外部协作者均为 mock，模板实际读取；这只证明零行分支缺陷，不冒充真实异步/MySQL 场景。

成功更新才登记失效；零行应有明确结果/事件，并记录是否继续原消息流程的取舍。补真实异步入口的零行样本及受影响的 S 修后/回滚；CACHE-007 暂不整项关闭。

## C：Redis 隔离和成本采样需要在本卡补齐

原卡明确要求 updateScore 使用隔离 Redis DB 或精确热榜协作者替身。现用 DB 0、无热榜替身，访问真实热榜 key 的路径未隔离。收尾时热榜为空不能证明隔离，不能把整改移到下一卡。代码只有在读到非空热榜时才执行 SET；没有热榜 I/O 原件，本次不认定执行报告中“真实写到热榜”已经被独立证明。

分档成本脚本以 `Get-Events ($tierStart - 50)` 统计事件，把 `requestId=tierread--1` 的预热回源混入采样，分母仍是 300 个正式读。按 300 个正式请求的 ID 重新归属：

| 每 10 读写数 | 成功写事件 PRE/POST | PRE 采样回源 | POST 原报告回源 | POST 采样回源 / 每百读 | POST 删除总/第二删 |
|---|---|---|---|---|---|
| 0 | 0/0 | 0 | 1 | **0 / 0.00** | 0/0 |
| 1 | 30/30 | 0 | 42 | **41 / 13.67** | 60/30 |
| 5 | 150/150 | 0 | 181 | **180 / 60.00** | 300/150 |

PRE 含预热的旧汇总实际为 0/1/1，并非交回消息中的每档 1。正确窗口下，双方 0 写档均为 300 命中/0 回源；POST 1/5 档为 259/120 命中、41/180 未命中。第二删造成的额外回源成本仍成立，不选参数，也不报物理 SQL 或 QPS。

分档 run 仅保存汇总 tiers.tsv 和事件，逐次读取响应、写入响应/提交时间列表只保留在内存。故分档“POST 陈旧 0/0/0、PRE 0/290/298”本次仅认可为执行者自检，不能独立从原始响应重算。现有 TSV 表头还写成了字面反引号 t；附加并发文件的数据行为竖线分隔，不能称合格 TSV。

先落实隔离，再以同字段初值重跑 B 与必需分档；保存每次响应/写入、合法表头、请求归属、第二删尾段和实际成功/失败数。新增 TOOL-007。附加并发组的有效历史观察保留，不要求为本卡再次扩展并发实验。

## D：固定 ID 夹具覆盖所有 ApArticle 新增请求

实际 P13bHarnessConfig 的条件仅为 `entity instanceof ApArticle`，随后返回 fixedId，没有匹配测试文章标记，也没有把其他新增文章请求委托原生成器。
