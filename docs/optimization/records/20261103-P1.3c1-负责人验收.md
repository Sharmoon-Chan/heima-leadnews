## A：任务先入队、后发布，关闭和完成可以越过发布

submitSecondDelete 在 `schedule` 返回后才加 accepted、放入 activeTasks；与 destroy 没有统一同步。注释用“单线程 + 500ms”保证赋值先于任务执行，但这不能保证提交线程一直获得调度。runSecondDelete 的 QUEUED 检查/RUNNING 写入也没有与 finish/cancel 用同一状态转换协议。

负责人没有修改受测 class。仅在离线夹具用 **真实 ScheduledThreadPoolExecutor 的返回门控**模拟提交线程在入队后被暂停；真实 runnable 仍在同一个真实工作线程执行，关闭经真实 Spring Context.close。该门控不是 mock 整个执行器；Redis 出口仍是记录替身，500ms 未改。

| 反例 | 实际结果 |
|---|---|
| 已入队、尚未发布时关闭 | Context 已关闭且 executor terminated=true，Future 已取消；释放提交线程后却变成 **accepted=1、queued=1、active=1、cancelled=0**，不会再有执行线程，取消任务和活跃引用遗漏 |
| 真实任务先完成、再发布 | delete 确实返回，succeeded=1；释放提交线程后 **accepted=1、succeeded=1、queued=0、running=0、active=1**，终态对象被重新放回活跃表。accepted 事件还晚于 begin/成功事件 |

这分别违反“关闭后的任务可对账/释放”和“活跃表只留排队或运行”。要求将提交成功后的接受/发布、开始执行与关闭/取消放在一致同步协议下；不是把 accepted 提前增加或补一个睡眠。QUEUED→RUNNING 与取消/终态也须原子协调，不能将已取消终态重新写回 RUNNING。

证据：`audit/publication-results.json`、`offline/race-results/*.events.log`。被测失效器 class hash 为 `89305c02…`，受测 class 与交付 target 相同。

## B：task_id 实际只在单个 Bean 实例内唯一

taskSeq 是实例字段，每个 Context 的失效器都从 0 开始。负责人在**同一个 JVM**顺序创建/关闭两个真实 Context，每个接受一个任务，实际 accepted 事件都为 **t42808-1**。

单 Context L1 的两个 ID 唯一成立，但不能升级为“进程范围唯一”。采用跨实例唯一的标识生成方式；每个 Bean 的业务累计计数可以独立，task_id 不能碰撞。保留明确的进程/实例边界，不依赖时间窗口排除重复 ID。
