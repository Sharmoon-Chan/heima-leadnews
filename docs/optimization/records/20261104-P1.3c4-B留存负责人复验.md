## 原B第二处：同步阻塞时仍漏已完成请求

最终`Complete-P13c4Get`在`task.IsCompleted`为真后才取当前时间，随后同时赋`ended_ms`与`Pending.completed_ms`。这记录的是**发现完成的时间**，无法测出此前Task已经完成多久。采样的`Send-Once`仍同步等待完整响应；3ms轮询只在它返回后或间隔期间运行。

负责人用最终helper及原AST精确提取的采样函数、私有loopback做独立客户端实验。独立Task continuation只观察状态和文件，**不调用被测Complete、不代替它落盘**：

1. 慢读完整响应Task已`RanToCompletion`时，另一条同步sample仍在等待。
2. sample阻塞期间7次观察账本慢读记录均为0；仅同步阻塞内可确定漏落盘至少**1445ms**。
3. 等sample返回再调用Complete后，`ended_ms`比独立首次完成观察晚**1578ms**、写入标记晚**1586ms**，自报lag却只有**8ms**。实验结束后的仪器读取开销另列，不把它全部算作同步请求阻塞。
4. 另用同一原函数，在慢读已完成而sample仍阻塞时中断被测客户端，慢读正文尚未入账。有限中断证明原B“完成/失败先落盘”的边界仍缺，不只是时间字段命名问题。

证据：[独立客户端完成实验](</D:/Code/Java/heima-leadnews/_optimization-artifacts/20261104-P1.3c4-Bfix-COMPLETION-REVIEW-r03/completion-probe-result.json>)与[中断审计](</D:/Code/Java/heima-leadnews/_optimization-artifacts/20261104-P1.3c4-Bfix-COMPLETION-INTERRUPT-REVIEW-r01/interruption-audit.json>)。只用私有HTTP出口；没有业务HTTP、数据库写入或旧归档写入。

25/25中的完成lag检查、`ended_ms == completion`以及真实31/31中的三条完成落盘检查，都使用收集器在同一次调用里赋的时间。它们证明观察后很快写入，不能独立证明真正Task完成后及时写入。`persisted_ms`在WriteLine/Flush之前写进行内，代表写入开始标记；`flushed_ms`才是Flush返回时间，本轮亦保留这个区别。
