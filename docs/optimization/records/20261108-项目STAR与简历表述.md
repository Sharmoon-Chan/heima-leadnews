# 黑马头条：量化 STAR 与简历表述

2026-11-08。依据：[本次补充压测报告](20261108-补充压测与量化结果.md)及此前 P1–P4 独立验收。数字对应本地受控实验，项目时间应标明后续优化发生于 2026.10–2026.11。工程交付与个人面试掌握是两回事，亲自复跑/复述状态仍为未验证。

## 简历可直接使用的版本

**微服务内容资讯平台（黑马头条）｜后端开发与性能优化**  
课程项目：2026.04–2026.07；后续优化与验证：2026.10–2026.11  
**技术栈：** Spring Boot、Spring Cloud Alibaba、MyBatis-Plus、MySQL、Redis、Kafka、Elasticsearch、MinIO。

基于课程项目完善面向自媒体创作者和 App 读者的资讯平台，覆盖发文审核、静态化、检索与内容分发；重点改造文章详情缓存、文章索引同步可靠性及连续分页，并使用 JMeter 和故障实验验证结果。

- **详情缓存与更新时序：** 为文章详情实现 Cache Aside、空值缓存和带所有权校验的互斥重建，将写后失效移至事务提交后；在本地 **1 万文章、100 ID 热集、20 req/s** 的三轮对照中，**每请求 DAO 调用由 2 次降为 0**，7,182 个测量样本零错误。
- **索引消息可靠性与重复抑制：** 修复 Kafka 消费异常处理，补充有限重试、确认式死信和指定消息重放；以业务 eventId 与 Redis 成功标记抑制重复索引，在 **8 个事件各投递 3 次** 的对照中，**ES 调用由 24 次降至 8 次，减少 66.7%**。
- **连续翻页正确性与深页开销：** 用 `publishTime + id`（文章 ID）复合排序的 `search_after` 游标修复同时间文章漏页，静态 123 条匹配集**漏项由 26 条降为 0**；在 **10 万数据、每页 20 条的实验 offset 对照**中，第 400 页单请求 **P95 三轮中位数由 20ms 降至 12ms（40%）**，不含游标准备成本。

这里每条都把背景/目标压缩在开头，接实施动作，最后给结果。篇幅有限时保留这三条即可；不必额外堆砌所有中间件参数或把 S/T/A/R 标签写进正式简历。

## STAR 1：详情缓存为什么要同时处理读路径和提交时序

**S｜情境**  
文章详情一次直读需要查询文章和正文，两次 DAO 调用。重复访问热门文章会重复回源；缓存失效时有并发重建问题，写库事务尚未提交就删缓存还可能让并发请求把旧值回填。这些问题在本地代码审查和受控时序实验中复现。

**T｜任务**  
在保持正文与字段契约一致的前提下减少热读回源，并处理不存在 ID、热点重建竞争和写后失效时序，拿到可对账的同代码 A/B 数据。

**A｜行动**  
采用 Cache Aside 和空值缓存；互斥重建使用唯一锁令牌、比较删除与有界退避，防止旧持有者误删新锁。将失效放到事务提交后，保留有界延迟第二删与任务生命周期观测。使用同一份代码，通过开关建立直读/缓存对照；固定输入、预热窗口、三轮顺序，按窗口、ID 和时间区间核对 JMeter 与服务端 DAO/HIT 的数量及一一配对；因未贯通请求 ID，不把它说成逐请求身份唯一可还原。

**R｜结果**  
本地 1 万文章、100 个热 ID、目标 20 req/s，三对测试 7,182 个有效样本、零错误，实测 19.93–19.97 req/s；DAO/请求 **2→0**，热集命中 **100%**，P95 三轮中位数 **4→3ms**。此前最终功能复测中，三轮各 12 个受控冷并发请求均只有一次重建，事务实验均观察到提交前旧值、提交后新值。

**面试收束：** “我的主要收益是减少重复回源。这里 MySQL 本来就很快，P95 只少了 1ms；500ms 第二删也不能保证强一致，慢回填越过窗口或进程退出仍是边界。”

## STAR 2：为什么有按 ID 覆盖写入，还要区分事件与失败终态

**S｜情境**  
项目在文章静态化后通过 Kafka 同步 ES 索引。原消费异常处理存在失败被当成正常返回的风险；按文章 ID 覆盖虽然不会新增重复文档，重复投递仍会重复调用 ES，同一文章的新修改又必须正常写入。

**T｜任务**  
让暂时失败能重试、持续失败有可确认的去向、指定消息可追踪重放，同时减少同一个业务事件的重复索引调用。

**A｜行动**  
把容器级错误处理器接到实际监听容器，对可恢复失败做首次处理后最多 3 次重试；死信发送等待确认，失败继续抛出，避免把“发起发送”当作“已恢复”。重放按来源坐标、eventId 和原始内容哈希绑定身份。生产端生成业务 eventId，消费端在 ES 写成功后记录 Redis 成功标记，后续同事件命中时跳过 ES；同文章新事件使用新 eventId。

**R｜结果**  
在同输入的 8 个事件、每个投递 3 次对照中，ES 调用从 **24 次降至 8 次，减少 66.7%**，16 次被成功标记拦截。已有故障实验覆盖暂时失败恢复、持续失败入死信、死信投递失败及指定重放；P4 三轮复测均验证对应终态。

**面试收束：** “按 ID 覆盖解决文档数量重复，eventId 成功标记减少重复副作用调用。它们都不等于 Exactly Once：ES 写与 Redis 标记/offset 之间并不原子，并发、崩溃、TTL 到期或事件乱序仍可能带来重复或旧值覆盖。”

**被问积压时再展开：** 在独立 4 分区、每次下游 ES 写增加 40ms 等待的实验中，将消费并发从 1 改为 2，三轮追平时间中位数 **16.255→5.431s，缩短约 66.6%**；正式 5,414 事件最终 lag=0。恢复观察有约 1 秒采样粒度。正常单分区仍保持并发 1，这不是生产吞吐提升 3 倍的证据。

## STAR 3：search_after 的首要动机是修复同时间漏页

**S｜情境**  
原接口使用“发布时间小于上一页最后时间”的时间游标。同一毫秒有多篇文章时，严格小于条件会跳过尚未返回的同时间记录；冻结实验中 123 条匹配记录只返回 97 条，漏了 26 条。原接口本身并不是大 offset 分页。

**T｜任务**  
先保证静态结果集连续翻页完整、排序稳定和大整数 ID 精度，再通过明确的实验 offset 对照量化深页访问成本。

**A｜行动**  
使用 `publishTime DESC, id DESC`（`id` 为文章 ID）完整排序元组和 `search_after`；游标保存首屏时间上界、查询指纹及最后一条实际返回记录的 sort 值，以 `size+1` 判断后续页，ID 用字符串返回。对多种页大小、坏游标、边界和动态变化分别验证；另外构造共用查询逻辑的 offset 实验端点，在 10 万条数据上做三轮原生 HTTP JMeter 对照。

**R｜结果**  
123 条静态匹配记录在多种页大小下全部返回、无重复，**漏项 26→0**。本次负载 2,424 条请求零错误，每个 case 每轮 100 条有效样本、共 2,400 条；第 400 页 P95 三轮中位数为 **实验 offset 20ms、search_after 12ms，下降 40%**。第 1/10 页无 P95 改善，第 100 页反而高 1ms，收益不能推广到所有页深。

**面试收束：** “我先修的是同时间漏项，再验证深页开销。第 400 页结果测的是已经拿到游标的单次请求；search_after 不支持随意跳页，固定时间上界也不是数据快照，更新、删除和补插旧时间仍会改变后续结果。”

## 30 秒项目概述

“这是一个基于黑马头条课程的微服务资讯平台。我后续重点改了三处：详情缓存通过事务提交后失效和互斥重建处理读写竞争，本地热集对照里 DAO 调用从每请求两次降到零；Kafka 索引同步补齐有限重试、确认式死信和事件判重，重复投递实验的 ES 调用减少 66.7%；连续分页改成时间加 ID 的完整游标，修复 26 条同时间漏项，并在 10 万数据第 400 页的实验 offset 对照里把 P95 中位数从 20ms 降到 12ms。所有数字都有原始记录，范围是本地实验。”

## 使用数字时的四个核对点

1. **20 req/s 是负载，不是最大 QPS。** 缓存热集全命中也不代表真实业务整体命中率 100%。
2. **66.7% 是该重复比例下的 ES 调用减少。** 不写成吞吐、响应速度或端到端成本提升。
3. **40% 的基线是实验 offset。** 不把真实旧时间游标冒充 offset；页深、页大小、数据量和游标准备边界应能口头说明。
4. **时间范围与工作内容如实填写。** 不把 2026.11 的补充优化倒填到原课程期；不加入本轮未验证的 JWT、延迟任务“只消费一次”、生产高可用或全链路零丢失表述。
