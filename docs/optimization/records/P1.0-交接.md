## 4. CACHE-006：冷热响应契约与大 ID 精度

### 4.1 根因（有代码依据）

`ConfusionSerializerModifier` 会对**任何 POJO 里名为 `id` 的属性**套用 `ConfusionSerializer`，把它写成字符串；
但 `Map`/`JSONObject` 里的数字不经过 Bean 序列化器。原实现：

- 冷读：`Map{article: ApArticle POJO, content}` → Jackson → `id` 是**字符串**；
- 热读：`JSON.parseObject(cached)` → fastjson `JSONObject` → Jackson → `id` 是**数字**。

原课程文章示例 `1302862387124125698` 是 19 位，本轮合成数据 `9007199254741xxx` 是 **16 位**；两者都大于 2^53-1，
前端按 double 解析会丢精度。所以热读那条路是错的，不是「语义相同的小差异」。

### 4.2 修复方式（最小、且对 A/B 都生效）

冷热统一用 `ArticleDetailVo` + 同一个注入的 `ObjectMapper` 写缓存/读缓存。响应结构不变（仍是 `{article, content}`）。

### 6.2 必须一起说的限制（不得只挑有利数字）

1. **不是容量结论**：闭环固定并发、单机、单实例，且**压测端与服务同机**抢 CPU。
2. **只跑了 1 轮**，未做 AB/BA 交替 3 轮，因此这些百分比是「本轮观测值」，不能当稳定收益；第三位有效数字没有意义。
3. **类级 `@Transactional` 仍在**：B 组缓存命中也要开事务、占连接，缓存的理论上限被压低（属 CACHE-003）。
   它是后续验证的潜在开销因素；本轮没有去掉事务的对照，不能据此解释确定的提升幅度。
4. 数据集是合成数据（固定 835 字符正文），不代表真实正文长度分布；课程库 26 篇未参与。
5. A 组第一次试验（`ab-A-with-sqldebug-unfair/`）**开着 SQL DEBUG** 跑过一遍，属不公平轮次，
