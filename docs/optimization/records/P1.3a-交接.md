### 2.1 语义改动（只有四处）

1. **只缩详情路径**：保留类级 `@Transactional`（`newPage` / `findNewsComments` / `saveArticle` / `updateScore` 边界不变），只给 `getArticleDetail` 加 `@Transactional(propagation = NOT_SUPPORTED)`，缓存命中、争锁、退避等待不再处于数据库事务中。
2. **一致快照收缩到短读事务**：文章 + 正文两条 SELECT 移入 `ArticleDetailSnapshotReader.load(...)`，`@Transactional(readOnly = true, propagation = REQUIRED)`；方法返回即归还连接，VO 组装、Jackson 序列化、`setEx` 回填都在事务之外。
3. **提交后失效**：`saveArticle` 的两个分支都改为 `detailCacheInvalidator.invalidateAfterWrite(id, reason)`。
   - 有实际事务：只登记 `TransactionSynchronization#afterCommit`，回滚不执行；
   - 无事务：立即执行 + 照现有 500 ms 策略安排第二次；
   - `afterCommit` 内直接执行删除，不再走 `invalidateAfterWrite`（避免把自己再登记一次）；
   - 删除失败只留痕计数，不改变已提交事实，第二次删除仍安排。
4. **删除失败/滞后不再静默**：`cache.evict.begin/ok/fail/second_scheduled/second_begin` 与 `tx.after_commit`、`tx.rollback_skip_evict` 事件齐全。

P1.2 的 UUID 令牌、Lua compare-delete、3000 ms 租期、1000 ms 等待预算、退避策略、TTL 与空值占位、响应字段与大 ID 字符串契约**均未改动**；500 ms 仍是原候选值，本卡不选参。

## 4. T1 关键时序（真实 MySQL 事务）

PRE（`P13a-PRE-T1-r01`，`events/PRE-all.log`）：

```
UPDATE(article/content)=V1  →  cache.evict(inside tx) 1793418983352  →  cache.evict(second, +500ms)
→  reader: cache miss → SELECT 读到 V0 → setEx(V0)  →  tx.hold.end 1793418986372  →  COMMIT(V1)
→  之后 detail 响应 = V0           ← 缺陷
```

POST（`P13a-POST-T1-r03`，`events/POST-all.log`）：

```
UPDATE=V1  →  cache.evict.register(inTransaction=true)  →  tx.hold.begin  →  reader 命中原有 V0 缓存（本次没有回填）
→  tx.hold.end  →  COMMIT  →  tx.after_commit 1793418801557  →  cache.evict.ok 1793418801558
→  之后 detail 响应 = V1           ← 修复
```

两次「读取连接隔离级别」：读取方在写方提交前看到的是 `V0`（MySQL 默认 `REPEATABLE READ` 下未提交写不可见），提交后重新回源读到 `V1`；脚本每次都用 `mysql -e "SELECT title"` 独立核对库内真实值，不以客户端返回时间戳代替 COMMIT 时刻（COMMIT 由 `tx.after_commit` 事件与 `tx.hold.end` 顺序共同确定）。

## 6. 口径与边界（读结论前必看）

- `db.enter/exit` 仍包住 `doQueryArticleDetail`（含序列化与回填），**不是纯 SQL 区间**；新增的 `db.snapshot.begin/end` 才是只读事务覆盖两次 SELECT 的区间。
- 连接占用用**应用层借用计数**（`conn_active/conn_borrows`，只观测包装）度量，不用 Hikari JMX（本栈未注册 MBean）。一次缓存命中在 PRE 造成 `borrows +1`、POST `+0`。
- 「无事务分支」（T4）是通过实验 harness 直接调用失效器验证的真实 Spring bean 路径；`saveArticle` 本身总是带事务，因此 T4 不冒充 `saveArticle` 的回滚/提交语义。
- 慢 DB/Redis 故障/屏障都是本轮夹具注入，**不是真实依赖故障**；未停共享 Redis/MySQL，未发 Kafka 消息，未访问真实 MinIO。
- 仍然不承诺：租期外严格互斥、HTTP 总耗时受等待预算约束、500 ms 窗口吸收任意回填、多实例部署下的延迟删除可靠性（P1.3c）。
- 单机、隔离库、单轮小样本；不构成容量结论，不报 QPS 收益。

### 10.3 C：T6 的运行时身份与正常等待命中


- 两条 SELECT 共用**同一个事务资源**（`resourceId` 相同）与**同一个连接对象**（`connId` 相同，identity hash）。
- 真实隔离级别 `isolation=4`（`REPEATABLE_READ`）、`autoCommit=false`，取自连接本身；不是另开 mysql 会话或硬编码。
- 冷读结束后 `conn_active=0`：短读事务已归还连接，随后才序列化与回填。
- 修前对照（`P13a-PRE-T6-r02`）`tx.trace` 计数为 0：没有短读事务可追踪，整段请求都在类级事务内。

正常等待命中（`P13a-POST-T6-r08`，探针 `db.delay.9007199254741014=600` 让持有者重建变慢）：

| 断言 | 原件 |
|---|---|
| 持有者先拿到锁 | `holder_holds_the_lock_before_waiter` pass |
| 等待者确实在等 | `lock.fail` **10** 次 |
| 结果正常 | HTTP 200 / 业务码 200 / `title=P1 article 14` / 耗时 **662.9 ms** |
| 精确 ID 契约 | 响应含 `"id":"9007199254741014"` |
| 等待者无回源 | 该请求的 `db.enter` / `rebuild.begin` = **0** |
| 等待期不持连接 | 采样 9 次，`conn_active` 峰值 **0** |

**口径必须写清**：这条样本的命中发生在「等待者最终拿到锁 → 锁后双重检查命中」（事件为 `lock.acquired` + `stage=recheck_after_lock`，判定键 `path=post_lock_double_check(DOUBLE_CHECK_HIT)`），**不是**等待循环内部的 `wait.end outcome=hit`。后者要求「持有者已经写好缓存但仍未释放锁」，而现有实现的写缓存与 finally 释放之间只有微秒级间隙，用当前夹具无法确定性复现，因此本轮**不声称**采到了该分支；两条分支都只是「等待后被缓存服务、且等待者未回源」，判定按实际观测到的路径记录，不预设某一条。原预算耗尽 503 样本（`t6.lock_wait_holds_no_connection`，14 次采样 peak=0）原样保留。
