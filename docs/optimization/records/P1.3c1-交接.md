## 1. 结论

- `DetailCacheInvalidator` 现在对每个第二删给出**进程内唯一 `task_id`**，状态只沿 `QUEUED → RUNNING → SUCCEEDED|FAILED|CANCELLED` 单向前进，终态只写一次；`accepted` 只在 `schedule` 成功返回后计数，拒绝按原因单列；成功只在真实 `delete` 返回之后记录。
- 关闭走**真实的 Spring 生命周期钩子**（`DisposableBean.destroy()`，经 `AnnotationConfigApplicationContext.close()` 实测）：先拒绝新提交，再有界等待，到期后取消未执行任务并计取消，最后写关闭回执。等待到期时仍在运行的 I/O 不被强写成功或失败，它的终态由它自己记录。
- **500ms 与单工作线程未改**；新增的唯一工程配置是关闭等待窗口 `p13c.evict.close-wait.ms`（缺省 2000ms），属工程配置，不是压测选参。

## 3. 状态与计数口径

- `task_id` = `t<pid>-<seq>`（进程内唯一，不依赖时间窗猜归属）。
- 计数（累计，单位：次）：`submit_attempts` = `accepted` + `rejected`（`rejected_closed` 关闭中拒绝、`rejected_scheduler` 执行器拒绝）；`accepted` = `succeeded` + `failed` + `cancelled` + `queued_now` + `running_now`。
- 当前数量：`queued_now` / `running_now` / `active_now`（活跃表只保留排队与运行中的任务，进入终态即移除）。
- 关闭回执：`closed`、`close_finished`、`close_wait_ms`（配置值）、`close_waited_ms`（实测）、`close_terminated`、`close_queued_before`、`close_running_before`、`close_cancelled`。
- 原有字段保留：`delete_attempts`、`delete_failures`、`after_commit_runs`、`no_transaction_runs`、`rollback_skips`、`second_delete_delay_ms`；`second_delete_scheduled` 现在**只统计成功接受**（旧实现先加后调度，拒绝也会被算进“已安排”），`second_delete_done` = `succeeded`，`second_delete_failures` = `failed`。

### 10.1 A：接受/发布、开始、关闭与终态共用一把状态锁

- 提交：`submitAttempts++` 与 `closing` 检查、**先写活跃表**、`schedule`、`accepted++` 与两条事件，全部在 `stateLock` 内完成；调度抛异常时撤回登记并只记 `rejected_scheduler`（不算接受）。
- 开始：`QUEUED→RUNNING` 也在 `stateLock` 内判定并写入，已取消/已终态的任务直接返回，不复活、不写第二个终态。
- 终态：`finish()` 在锁内改状态、累加计数**并且**从活跃表移除，终态对象不可能被写回。
- 关闭：先在锁内 `closing=true` 并 `shutdown()`（此后提交一律拒绝，刚入队任务一定被接手），**在锁外** `awaitTermination`（否则运行中任务无法写终态），再在锁内做取消登记与 `shutdown_end` 回执。
- 取消：`cancel(false)` 成功、`future.isCancelled()`、或执行器已 `terminated`（该任务永远不会再执行）三种情形都计 `CANCELLED`，不留“已取消仍在活跃表 / 排队却永不执行”的残留；等待到期仍在运行的 I/O 不中断、不替它宣布结果。

反例复现（真实 executor + 真实 `AnnotationConfigApplicationContext.close()`；仅为竞态用例把**提交线程在入队后**暂停，executor 本身未 mock）：

| 用例 | 补修前（负责人独立复现） | 补修后（本轮实测） |
|---|---|---|
| 已入队、未发布时关闭 | accepted=1、queued=1、active=1、cancelled=0，future 已取消且 executor 已 terminated → 残留 | `accepted=1`、`cancelled=1`、`active=queued=running=0`、`begin=0`、第二删未到达出口（仅 1 次 delete，即第一删）、组件线程 0 |
| 任务真完成后才发布 | accepted=succeeded=1、q/r=0 但 **active=1**（终态被写回活跃表） | 该倒序不再可能出现：worker 拿不到锁就无法进入 RUNNING；`accepted` 事件先于任何 `begin` |
| 关闭后才提交 | — | `submit_attempts 0→1`、`accepted=0`、`rejected_closed=1`、`active=0` |
| 排队即被关闭 | — | `queued=1/running=0` 时关闭：`cancelled=1`、`succeeded=0`、`active=0`、`begin=0` |
