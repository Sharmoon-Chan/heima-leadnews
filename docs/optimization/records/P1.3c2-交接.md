## 1. 结论

- 上限即**活跃表大小**：`max_active = queued_now + running_now`。检查、登记、释放在同一把 `stateLock` 内完成，因此并发提交不越界；没有隐藏队列，被拒的任务**不进入**活跃表。
- 超限**只拒第二删**：第一删照常执行，写结果与提交行为不变；被拒的第二删只计入 `rejected_backlog`，与 `rejected_closed` / `rejected_scheduler` 并列单列，不混算。
- 名额在**终态只释放一次**（成功/失败/取消都在同一把锁内移出活跃表并计数）。
- 上限是正整工程配置 `p13c.evict.max-active`，缺省 **256**（工程约束，不是压测选参）；`< 1` 在构造时抛 `IllegalArgumentException`，不静默回退默认值。
- 原有九个 stats 字段全部保留；新增 `rejected_backlog`、`max_active`、`active_peak`，且 `rejected = rejected_closed + rejected_scheduler + rejected_backlog`。

## 3. 计数与事件口径

- `submit_attempts` = `accepted` + `rejected`；`rejected` = `rejected_closed` + `rejected_scheduler` + `rejected_backlog`。
- `accepted` = `succeeded` + `failed` + `cancelled` + `queued_now` + `running_now`（收敛后前四项之外为零）。
- 拒绝事件：`event=cache.evict.second_rejected reason=backlog taskId=t<pid>-<seq> articleId=<id> phase=updateScore:afterUpdate:afterCommit maxActive=<n> active=<n> peak=<n> key=…`，可直接按 `articleId`/`taskId` 归属，不需要时间窗猜测。
- `active_peak` 是**进程内**观测峰值，只在锁内更新；可从 `second_accepted` 事件的 `active=` 独立复算。

## 4. 离线 Q1–Q5（`P13c2-LIMIT-r02`，35/35）

真实组件：交付的 `DetailCacheInvalidator` + 真实单线程 `ScheduledThreadPoolExecutor` + 真实 500ms + 真实 `stateLock` + 真实 `DisposableBean` 关闭（`AnnotationConfigApplicationContext.close()`）。唯一替身是 Redis 出口（`RecordingCacheService` 只记录 `delete(key)`），**不能当作 Redis 服务器证据**。冻结测试值：`max_active ∈ {2,1}`、慢第二删 1200ms、关闭等待 ∈ {2000,300}、延迟 500ms。

| 组 | 判断 | 实测 |
|---|---|---|
| Q1（max=2，20 次提交） | 只有上限在拒，活跃表不被穿透 | `accepted=2`、`rejected_backlog=18`、`submit_attempts=20`、`active=queued=2 running=0`、`delete_attempts=22`（20 次第一删 + 2 次真正执行的第二删）、`active_peak=2`；18 条拒绝事件全部 `reason=backlog` 且带 taskId/articleId/phase；从 `second_accepted` 事件复算峰值 ≤ 2；收敛后 `accepted=succeeded=2`、`active=0` |
| Q2（max=1） | 满时拒绝，名额随成功/失败/取消归还 | 满时 `active=1` → `rejected_backlog=1`、`accepted=1`；成功后 `succeeded=1 active=0` → 再提交 `accepted=2`；失败后 `failed=1 active=0` → 再提交 `accepted=4`；关闭前提交使 `accepted=5`，关闭后 `cancelled=1 active=0`；最终 `accepted=5 = succeeded 3 + failed 1 + cancelled 1`、`submit=6 rejected=1`、`active_peak=1` |

| Q4（max=2 满载后关闭） | 满载关闭仍按关闭契约收口 | 满载 `active=2 accepted=2 rejected_backlog=1`；关闭后 `cancelled=2 active=0 close_finished=1 close_cancelled=2`；关闭后再提交 `rejected_closed=1 accepted=2`（写结果不变）；存活 `p13a-cache-evict` 线程 **0**；`delete_attempts=4`（3 次命中上限内的第一删 + 1 次关闭后提交的第一删），**无第二删执行** |

## 8. 边界（不要过度解读）

- 上限是**本组件、本进程内**的活跃表上限：跨进程、多实例、崩溃后重启都没有保证，也没有持久化补偿。
- 上限不是队列消费能力，也不是「每篇文章一个名额」；同一文章连写同样受限。
- 未调 500ms，未改单线程与执行器类型，未改锁结构、事务注解、公开响应格式。
- 本卡不报容量、QPS、命中率或任何选参结论；256 只解释为工程默认值。
- 离线 Q1–Q5 的 Redis 出口是替身；真实 Redis 行为只由 Q5 的应用样本覆盖。
