## 1. 结论和适用范围

在本机隔离数据库约 1 万篇文章中，固定访问 100 个存在 ID，以相同代码关闭/开启详情缓存。三对实验的 **5,399 个测量样本全部成功**。A 组应用侧 DAO 调用/请求为 2，B 组为 0；缓存 HIT 占比从 0% 到 100%。这证明本次热集负载下减少了回源调用。

三轮分位数的中位数：P50 为 3→2ms，P95 为 4→2ms，P99 为 5→3ms。P50/P95 在这三对中都较低，但差值只有 1–2ms；不作统计显著性声明。A 的 P99 在 4–13ms 间波动，不主张稳定尾延迟收益。本次没有证明生产容量、20 req/s 承载上限、冷缓存/空值/写入混合负载收益，也不将 A 称为历史旧版本。

## 2. 条件与实际负载模型

| 项目 | 实际条件 |
|---|---|
| 接口 | `GET /api/v1/article/detail/{id}` |
| A / B | 同代码，`article.detail.cache.enabled=false / true` |
| 端口与数据 | A 51821、B 51822；`leadnews_article_p1`，Redis DB5；两服务同时在线，顺序施加负载 |
| 构建 | 相同 target/classes 路径、依赖路径；两份实例记录的 6 个关键 class hash 一致，并与复核时磁盘文件匹配；不将此扩称为全部依赖内容冻结 |
| 服务 JVM | JDK 1.8.0_451，`-Xms128m -Xmx256m -XX:+UseParallelGC`，javaw 启动；两侧参数除端口与缓存开关外一致 |
| JMeter | 5.6.3，非 GUI，无插件；`-Xms64m -Xmx256m -XX:MaxMetaspaceSize=192m -XX:ReservedCodeCacheSize=64m` |
| 请求输入 | 100 个字符串 ID（均大于 2^53−1），每线程独立顺序循环同一 CSV；六组均覆盖全部 100 ID，每 ID 8–10 个测量样本，实际次数并非严格相等 |
| 节拍 | 原生线程组 2 线程，3s 爬坡；Constant Throughput Timer 300 samples/min，`calcMode=1` |
| 时长及顺序 | 每相位 240s；以首样本时间为起点排除前 60s，统计随后 180s；A→B、B→A、A→B |

`calcMode=1` 在本地 5.6.3 的枚举中是 `AllActiveThreads`，并非带 `(shared)` 的模式；本计划只有一个线程组。它给现有线程加入等待来接近目标吞吐，线程不足或请求变慢时会达不到目标，**不能称为严格开环固定到达负载**。本次采用“固定线程数、吞吐计时器节拍控制”的低负载模型。

依据：JMeter 随包 `printable_docs/usermanual/component_reference.html` 的 Constant Throughput Timer 节，以及 `lib/ext/ApacheJMeter_components.jar` 中 `ConstantThroughputTimer$Mode`。负责人使用本地官方发行包核对，未将无返回内容的在线访问当作验证证据。便携包 SHA-512 实算与交付记录的 `387fadca…` 一致；官方校验文件下载过程属于执行者记录。

## 3. 正确性与失败尝试

同代码预检：A/B 各 100 个唯一 ID、100/100 正确，核对 HTTP/业务 200、ID 字符串、四计数/channel/author、正文 UTF-8 字节数及 SHA-256。预检记录在正式实例重启前生成，不能称为重启后逐项正文 hash 复验。正式 JMX 持续断言 HTTP/业务码、精确字符串 ID、字段与正文长度，负载期未重新计算正文 SHA-256。

负向对照有 120 条记录，6 条失败，分别为错误 views、正文长度、不存在 ID，各被拒绝两次；不纳入性能结果。5 req/s 小试 A/B 各 75 条成功。20 req/s A 的尝试为启动失败、零样本，没有形成可用成对比较，**不能据此说业务扛不住 20 req/s**。

最终六相位共保留 8 次零样本失败重试；六次纳入统计的进程均 exit 0，均有两个线程正常结束和 JMeter end-of-test 日志，首末请求覆盖 239.792–239.844s。此前两次有样本的无效运行保留于 `_invalid-server-down`：235/234 条全部连接拒绝，按服务不可用排除，随后重做整对。无须因报告口径问题重跑这些有效原始数据。

原 runner 仅用“样本数大于零”判 accepted，`accepted_rows` 也为 null，不能单独作为有效轮凭据；本次负责人直接核对了退出码、原始行数、时间和结束日志。原统计的 `latency_ok_ms` 漏排序，六组该辅助字段均有错误，停止引用；本报告和负责人 `review-stats.json` 已分别排序全部/成功样本后计算。

## 4. 三对结果

延迟单位 ms，最近秩法。吞吐统一为测量样本数/名义 180s 窗口。原来的 5.006–5.011/s 用“最后一个请求开始减第一个请求开始”作分母，属于另一种观测跨度口径，不表示超额承载能力。

| pair1-A | 1194 | 294 | 900 | 0 | 3 | 4 | 13 | 53 | 5.000/s | 2 | 0% |
| pair1-B | 1192 | 292 | 900 | 0 | 2 | 3 | 3 | 3 | 5.000/s | 0 | 100% |

最后一组 899 条如实保留，不补样本、不假定丢失一个请求。增加明确窗口上界 `[首样本+60s, 首样本+240s)` 后没有超窗样本，原主分位数全部复算一致。A 共 2700，B 共 2699。

| 三轮分位数的中位数 [范围] | A 关缓存 | B 开缓存 |
|---|---:|---:|
| P50 | 3 [3–3] | 2 [2–2] |
| P95 | 4 [3–4] | 2 [2–3] |
| P99 | 5 [4–13] | 3 [3–3] |

服务端 `[DETAIL-METRIC]` 在同一采样时间窗内的行数与 articleId 多重集，六组均与 JTL 一致。A 三组均为 900 个 DB_HIT、1800 次应用侧 DAO 调用；B 为 900/900/899 个 HIT、DAO 0。第一对的“时间±1s + articleId”存在多个候选，无法唯一绑定每条请求；因此采用窗口聚合核对，不声称全量逐请求唯一对账。

`dbSelect` 是代码中记录的 DAO 调用数（文章、正文各一次），并非数据库服务器物理 SQL 计数。`costMs` 是详情 service 方法入口至打点的耗时，不等于纯 MySQL 耗时，且未包含后续响应序列化和传输。A 三轮该字段中位数均为 1ms；本报告撤回“本地 MySQL 本身约 3ms”的因果解释。没有 GC 事件证据，不将延迟尖峰归因于 GC。

## 5. 环境偏差与收尾

两侧因 Nacos 连接被拒而关闭 config/discovery，共用 `config/p14c-local.yml`；两份启动参数表明 A/B 一致，但不是使用在线 Nacos 的生产环境。准备阶段曾出现低可用内存，随后对称降低 JVM 堆。最终六次有效运行的前后可用内存快照为 1708–4171MB；`resources/` 为空，没有持续 CPU/GC/资源余量曲线，不能声称全程排除客户端或内存干扰。

若干启动进程记录 `0xC0000005`；根因未隔离，不宣称由堆大小引起或与内存无关。早期服务停止且日志见 `^C`，可记录后续改用 javaw 并正常完成，但不足以独立证实是哪一个清理动作广播中断。

执行者收尾证据记录：Redis DB5 逐个删除本卡精确 key，100→0，DB0=0；停止本卡实例。负责人再次只读检查 Redis DB0/5 均 0、本卡端口无监听；独立 SELECT 确认数据库两表仍各 10000 行，冻结的 100 ID、六字段、标题、正文 SHA-256 与字节数均匹配，0 差异。此项覆盖指定测试数据，不声称逐字段复核了整个数据库。不依据进程快照概括“全机只剩 3 个 Java”。

## 7. 面试说明（约 60–90 秒）

我为黑马头条文章详情实现了 Redis 缓存，并用同一份代码的缓存开关做对照。使用 JMeter 非 GUI 模式，固定 100 个存在文章 ID、2 个线程，吞吐计时器目标为每秒 5 次请求。每组预热 60 秒后测 180 秒，做了三对并交替顺序。

有效测量共 5399 次，全部通过状态、ID 和字段断言。热缓存组应用侧 DAO 调用从每请求 2 次变成 0 次，命中率 100%。三轮 P50 的中位数从 3ms 降到 2ms，P95 从 4ms 降到 2ms。这里最扎实的结果是减少回源；毫秒级延迟差异较小，P99 也有轮间波动，所以我不会包装成大幅提速或生产容量。这个实验覆盖本机低负载和固定热集；冷缓存、混合写与故障行为由其他功能验证分别说明。
