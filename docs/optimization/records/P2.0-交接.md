## 1. 真实链路（全部以源码为证，不是简历说法）

| # | 步骤 | 谁触发 | 与 HTTP 返回的关系 | 是否 Kafka |
|---|---|---|---|---|
| 1 | 自媒体自动审核（文本/图片）→ 组装 `ArticleDto` | `wemedia` `WmNewsAutoScanServiceImpl`（`@Async` 审核线程） | 与用户 HTTP 无关 | 否 |
| 2 | 调 `articleClient.saveArticle(dto)` | 同上，**Feign HTTP 同步调用** | 服务间同步调用 | **否（不是 Kafka）** |
| 3 | 写 `ap_article` / `ap_article_content` | article `ApArticleServiceImpl.saveArticle`（类级 `@Transactional`） | 同步，**在 HTTP 响应前完成** | 否 |
| 4 | 触发 `buildArticleToMinIO(apArticle, content)` | 同一方法末尾 | `@Async` → **与 HTTP 响应解耦** | 否 |
| 5 | Freemarker 渲染 `article.ftl` → HTML | 异步线程池线程 | 解耦 | 否 |
| 6 | `uploadHtmlFile(...)` → **MinIO** 上传，得到 path | 异步线程 | 解耦（阻塞网络调用，只在异步线程） | 否 |
| 7 | `update ap_article.static_url = path` | 异步线程 | 解耦；HTTP 响应里**没有** static_url | 否 |
| 8 | 详情缓存失效（P1.3b `DetailCacheInvalidator`） | 异步线程 | 解耦 | 否 |
| 9 | `createArticleESIndex` → `kafkaTemplate.send("article.es.sync.topic", JSON(SearchArticleVo))` | 异步线程 | 解耦；**fire-and-forget**（原实现丢弃返回值） | **是（生产侧）** |
| 10 | search `SyncArticleListener` 消费 | search 服务监听容器 | 与 article 无关 | **是（消费侧）** |
| 11 | ES `IndexRequest("app_info_article").id(articleId).source(message)` | 消费者线程 | — | 是（消费后的副作用） |
| 12 | ES refresh（默认 1s）后可被 `_search` 查到 | ES 自身 | — | 否（ES 内部） |

**必须写明的两点**

1. **“Kafka 异步审核”不成立**：审核发生在 `wemedia` 内部，之后用 **Feign HTTP** 调 article 服务；Kafka 只承担“文章 → ES 索引”这一条同步链路（第 9–11 步）。
2. **“static_url/静态化是同步的”也不成立**：第 5–9 步全在 `@Async` 线程里，`saveArticle` 的 HTTP 响应返回时 static_url 往往还没写、ES 更没索引。因此“提交成功”不等于“已静态化”或“已可搜索”。

链路里**与 HTTP 返回解耦**的步骤：5–9（渲染、MinIO、static_url 回写、缓存失效、Kafka 发送）。
链路里**属于 Kafka** 的步骤：9（生产）、10（消费）、11（写入 ES 的副作用）。

## 5. 整篇正文日志：已查明，已改

**原实现**：
```java
log.info("SyncArticleListener,message={}",message);   // message = 含整篇正文的 JSON
```
- 每条消息把完整 JSON（含 `content` 全文）写进**控制台 + 文件**，在消费线程上同步 append。
- 量级：本数据集 `content` 恒为 **835 字节**（100/100 条，来自 P1.4c 冻结真值 `ids-truth.json`，sha `6a94e406…`），加字段后实测单条响应约 **1292 字节**；真实文章正文远大于此。
- 结论：**会影响后续吞吐/积压实验**（P2.3），既是 CPU/IO 成本也是磁盘成本，而且日志级别是 INFO 属于默认开启。

**改法**（`SyncArticleListener.java`）：
- INFO 只打 `articleId` + `messageBytes`；
- 完整 payload 降到 `DEBUG`（需要时才开）；
- 解析失败/缺 id 的诊断改成**有界**输出（`bytes` + 头部 256 字符），且解析失败**仍然向上抛**（重试/死信归类属 P2.1，语义不变）。

## 6. producer 发送结果观测：已补

**原实现**：`kafkaTemplate.send(topic, JSON)` 的返回值被丢弃 → broker 不可用、发送失败时，调用方与日志都看不到任何结果。

**改法**（`ArticleFreemarkerServiceImpl.createArticleESIndex`）：
- 拿 `ListenableFuture<SendResult<String,String>>` 并 `addCallback`：
  - 成功：`[ES-SYNC-SEND] ok articleId=… topic=… partition=… offset=… bytes=…`
  - 失败：`[ES-SYNC-SEND] fail articleId=… topic=… bytes=… error=…`
- **不改**同步语义（仍是异步发送，不在请求线程上等待）；
- **不声称**解决了数据库与消息的原子性；
- **仍然不指定 key**（与改动前一致，因此不保证同文章分区内顺序——是否加 key 属于 P2.2 的决定，本卡不擅改分区行为）。
