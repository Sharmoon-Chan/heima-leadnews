# P2.1：Kafka重试、死信与指定消息重放

执行：2026-11-08，Asia/Shanghai。用户要求由负责人直接接手执行本卡。实验根：`D:/Code/Java/heima-leadnews/_optimization-artifacts/20261108-P2.1-MQ-r01`。

**结果：本卡实现与有限故障验证通过。** 22个broker确认的原始测试事件最终分为13个ES已处理、9个DLT隔离，未决0。4次人工重放属于原事件的重复投递，另记回执；原始DLT共11条，包含已成功重放的2个事件，不能把“待处理事件数9”与“DLT物理记录数11”混为一谈。

## 1. 具体改动

- `SyncArticleListener`：空白、非法JSON、缺失/非法articleId以及ES400/422归为不可重试，直接进入DLT；ES429/503、网络和IO等操作故障仍可重试。保留原message/key，并记录源topic/partition/offset、eventId或源坐标、attempt和结果。默认topic/index保持课程值，增加可覆盖参数便于独立实验。
- `KafkaErrorHandlerConfig`：原生 `SeekToCurrentErrorHandler` + `FixedBackOff(1000,3)`，即首次后最多3次重试；添加异常分类，开启原生delivery attempt header。DLT失败保持未恢复，源消息继续等待处理。
- `ConfirmedDeadLetterPublishingRecoverer`：保留2.6.6原生DLPR构建消息、源坐标和异常headers的逻辑，只替换publish边界，等待send Future的broker确认。同步异常、异步异常、超时和中断均上抛；中断标记恢复。未确认投递不能被记为恢复成功。
- `P21ReplayCli` / PowerShell入口：默认预览，只选择明确DLT topic/partition/offset + eventId。执行需再次确认原目标topic及预览payload SHA256，保留原字节和headers，追加重放身份；逐条限速，共用journal串行落盘意图和确认结果，不提交DLT消费offset，不全topic重放。

本地实际Spring Kafka **2.6.6** 的DLPR没有新版 `setFailIfSendResultIsError` 等接口；其原publish对同步/异步发送失败只记录日志。此行为已由使用原类的单元测试复现，故采用小范围继承封装，未升级依赖。Kafka client仍为**2.5.1**。

## 3. 有限故障结果

| 场景 | 实测 | 关键证据 |
|---|---|---|
| 正常 | 1次处理，ES version1 | `result-normal.json` |
| ES前两次503后恢复 | attempt 1/2/3，第3次成功；相邻调用间隔1164/1018ms | `result-transient.json`、proxy原日志 |
| ES持续503 | 原记录共4次，间隔1016/1014/1027ms；DLT确认main.DLT p0 offset0，后续正常消息继续 | `dlt-after-persistent.json`、main-02日志 |
| 空白/非法JSON/缺id/ES400 | 各1次，直接DLT，原始payload和异常headers保留；随后正常消息成功 | `final-main-dlt-0.json` |
| DLT producer指向不可达broker | 2000ms元数据等待超时、dlt-unconfirmed；失败源分区无提交，后续消息404；恢复后提交2 | `down-offset-blocked/recovered.json` |
| DLT缺源分区1 | 客户端超时而非回退到分区0；源分区1无提交、后续404；改用有分区1的测试DLT后提交2 | `narrow-*`、main.DLT分区1记录 |
| broker拒绝DLT（minISR2但只有1副本） | `NotEnoughReplicasException`；源offset保持2，恢复minISR1后推进到4 | `isr-*` |
| 真正的异步投递确认超时 | 已连接broker，反复拒绝后Future报 `TimeoutException: Expiring 1 record(s)…3000 ms`；源offset保持7、后续404，恢复后推进9 | `delivery-clean-*`、delivery-timeout-01日志01:08:45.243 |
| 消费前停机 | 停机时入队，ES不存在；启动后处理成功 | `restart-before-*` |
| ES已成功、offset提交前重启 | 真ES先写version1，源提交仍为13；中断实例后重启，源offset13再次处理，ES version2、提交14 | `restart-after-*` |
| 指定重放/重复重放 | persistent DLT p0 offset0被显式重放3次，source offsets10/11/14，ES同ID最终version3；重复ReplayId拒绝 | `replay-journal.jsonl`、`replay-final-es.json` |

上述每种DLT故障期间，同分区后续消息都没有被偷偷跳过；恢复失败目标后才继续。DLT不可达、缺分区、ISR失败的源记录分别被重新调用8/6/11次，原生attempt header可反复为1；这不是8/6/11次ES业务重试，而是DLT未恢复导致的重新投递。attempt不是跨重启持久计数。

## 4. 终态对账

逐事件明细在 `evidence/scenario-summary.json`，由源发送回执、消费者实际日志、DLT读取及ES观察离线生成。

- **22个原始唯一事件**：11个直接/重试/重启后成功，2个经人工重放成功，9个仍以坏消息隔离在DLT，未决0。
- **26条源topic物理记录**：22原始发送 + 4次人工重放；最终提交为main分区0=15、down分区0=9、narrow分区1=2，合计26。
- **11条DLT物理记录**：9个尚待人工业务处置的错误事件，加2个已重放成功但仍保留审计记录的事件。11条原payload均与输入逐字节相同，源坐标、eventId、异常元数据齐全。
- 人工重放第4次用于恢复一次实验环境问题导致的合法消息DLT；原样记录，未删除失败样本。

## 5. 实验中修正的实际问题

1. Windows独占FileChannel锁下，重放工具最初另开句柄读journal失败。改成持同一channel读写，补持锁读写回归；原失败日志保留，失败发生于发送前。
2. 监听器可选groupId最初默认空字符串，隔离配置显式赋值时未暴露，正常启动时报 `InvalidGroupIdException`。已改成显式回退 `spring.kafka.consumer.group-id`，重新跑12项测试并真实重启；正常 `leadnews-search` 已分配 `article.es.sync.topic-0`。错误实例已停，其日志保留。
3. 最后的投递超时补测先复用了已停止的ES代理，后续合法消息因ES不可达进入DLT。恢复代理后按精确DLT坐标/eventId/SHA重放成功，并新增干净超时轮验证预期后续进度。两轮都进入总账，没有挑结果丢样本。
4. 首次独立实例的应用组件未全部扫描，启动日志保留；classpath规范化后正常。组件索引在该环境不存在，不能将其写成已证根因。启动器只报告HTTP监听还不足以证明可消费，本次最终另核了真实分区分配。

## 7. 使用与边界

人工重放入口和精确命令见 `benchmarks/kafka/REPLAY-P21.md`。本工具故意限定本卡 `p21-20261108-*` topic和明确eventId header；普通旧消息没有该header时，不会自动猜测或整topic重放。P2.2再设计业务事件协议。本卡所有人工调用必须共用同一journal；未确认发送或只留intent时，先对账再决定是否重发。

正常服务入口仍为 `benchmarks/env/start-p2-instance.ps1`，默认EnvironmentRoot现指向本实验根中新生成的本地配置；在线和离线来源保持一致。老环境配置及脚本作为历史原件保存，不能拿来覆盖新配置。

**保留的限制：** 没有数据库/MQ原子事务、消费事务或业务事件去重；ES写入与源offset提交之间仍有重复窗口。DLT Future超时后可能晚到成功，因此再投DLT可能重复。人工重放/ES同ID覆盖不保证旧事件不会覆盖新内容。DLT故障期间同分区会阻塞，需要修复后恢复处理。单broker/单副本即使acks=all也不是生产高可用或零丢失证明。本卡不做吞吐测试，不进入P2.2。
