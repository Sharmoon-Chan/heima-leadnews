## 1. 对照结果

同一代码、同一24条消息序列、同一ES索引与故障代理，8个eventId各重复投递3次。先关去重，再开去重；关组不写Redis成功标记，开组从未命中开始。两份输入文件逐字节一致；日志按源topic/partition/offset精确归入两组，避免后来复用eventId的冲突用例混入。

| 指标 | 关闭去重 | 开启去重 |
|---|---:|---:|
| Kafka投递/实际调用 | 24 | 24 |
| 唯一eventId | 8 | 8 |
| 实际ES写入调用 | 24 | 8 |
| dedup-hit | 0 | 16 |
| Redis GET | 0 | 24 |
| Redis成功标记写入 | 0 | 8 |
| 每ID在本组增加的ES version | 3 | 1 |

本样本重复比例为16/24，ES写入减少16次，即66.7%。这不是根据文档总数推断：ES代理逐请求回执、服务日志和版本增量相互对应。无重复的首次投递均正常写入；后续重复才被拦截。

**成本也有记录：** 开组24次Redis查询耗时中位数约2.600ms，8次标记写入中位数6.610ms；首次连接使单次查询达到1.111s，查询总计1.262s、标记写入总计65.378ms。关组ES调用总计1.013s，开组307.755ms。它们是本地代理下、未预热的有限观察，不能相减当作端到端提速或QPS收益；本卡只主张重复ES调用减少，不声称延迟整体改善。

证据：`comparison-off/on-result.json`、`send-comparison-off/on.json`、`logs/off-01`、`logs/on-01`、ES/Redis代理日志和`scenario-summary.json`。

## 2. 正确性与故障

| 场景 | 实际结果 |
|---|---|
| 旧原始文章消息投递两次 | 两次ES写入、version2，无业务成功标记；header存在也不冒充新协议 |
| 同文章两次不同eventId | 两次均应用，第二条内容生效；不会按articleId永久拦截 |
| 同eventId变更内容 | 既有标记指纹冲突，具名不可重试并进DLT，原文档不被覆盖 |
| Redis读失败 | 注入GET错误，实际ES成功，之后可写标记；恢复后同事件重复被拦截 |
| Redis写失败 | 实际PSETEX/SETEX错误发生于ES成功之后，文档存在而标记不存在；不触发假ES失败。恢复后同事件再处理，version1→2并留标记 |
| 并发相同eventId | 两个分区、两个监听线程在未留标记时各写一次，真实version2；标记出现后下一次重复被拦截 |
| ES持续503 | 4次尝试后确认DLT，ES目标404、成功标记不存在；P2.1行为保持 |
| DLT原事件重放两次 | 原封装/eventId/key保留；第一次成功后version1，第二次dedup-hit仍version1 |
| TTL | 实验TTL5s内重复不写ES；标记过期确认不存在后再次写入，version1→2。正常配置仍24小时 |
| ES成功、标记前崩溃 | Redis代理在实际写标记前挂起，ESversion1且Redis无标记；停止该测试JVM时源commit68，重启后同记录再处理为version2，commit69并留标记 |
| 旧事件晚到 | 新事件先到、另一个未见旧事件后到，最终旧内容覆盖。明确无版本顺序保护 |

Redis故障代理只限制本卡`p22:`key，故障解除后正常转发。ES代理只允许本卡索引。没有停共享Redis/ES来注入故障。崩溃用例为给定窗口将Redis命令超时临时设10s，以在等待标记时精确停止JVM；普通配置/其他故障命令超时500ms。该窗口验证不是对生产崩溃率的估计。

## 3. 真实生产端连通

在隔离article实例（51822）调用真实 `POST /api/v1/article/save`：创建一篇文章，再更新同一ID `2119123088405827586`，使用合法JSON数组正文。两次均经异步静态化、MinIO、真实KafkaTemplate发送到本卡独立topic，再由真实search监听器消费。

- 两条消息schemaVersion均1，articleId为同一个精确十进制字符串，eventId为两个不同UUID。
- Kafka key均等于文章ID，观察到相同分区；header eventId与封装一致。
- ES只含payload字段，无schemaVersion/eventId/payload封装字段；同文档version2。
- 两个事件均有成功标记；对应MinIO对象真实存在、含本卡正文标记，第二版原始HTTP响应8273字节。
- 这是一次逻辑调用生成一个ID的验证，不证明上游重复HTTP请求可识别为同一逻辑请求。

证据：`real-producer-create/update-response.json`、两分区Kafka原始读取、`real-producer-wire-check.json`、ES及静态文件观察、生产者与消费者日志。

## 6. 可以认领与不能认领

可以说：增加稳定业务事件ID，使用Redis记录ES已成功处理的事件，在本次固定重复样本中将24次ES写入减少为8次；保持旧格式兼容，明确验证Redis故障、TTL和并发/崩溃时的行为。

不能说：Exactly Once、并发重复始终只写一次、旧事件不会覆盖新内容、Redis永久保留身份、上游save请求天然去重，或本次已证明吞吐/延迟的生产收益。成功标记仅是降低重复副作用成本，不是事务性协议。本卡不进入P2.3。
