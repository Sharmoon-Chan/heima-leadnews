# CACHE-006：缓存命中后的 ID 类型与精度边界

类型：本地接口契约缺陷，P1.0 已在隔离 API 样本修复并验收；不是生产事故。代码由执行 agent 完成，用户独立复述/复跑：待确认。证据见 [P1.0 负责人审阅](../20261029-P1.0-负责人审阅.md)。

## 现象与根因

同一文章冷读和热读的响应不同：数据库返回 ApArticle POJO，经项目 Jackson 模块将 id 序列化成字符串；旧缓存读取经 fastjson 转成 Map，绕开 Bean 属性序列化器，id 以数字输出，null/缺省策略也不一致。

Java Long 在服务端没有因此丢精度；风险出在 JSON 数字被客户端按不能精确表示该值的数值类型解析。只看“字段有 id、业务码 200”发现不了这个契约差异。

## 修复与验证

冷热统一为 ArticleDetailVo，缓存用同一注入 ObjectMapper 写入并读回类型对象。A 组直查也使用该 VO，公共契约修复同时作用于两组。

用 9007199254741007 作为样本：它是 16 位、超 2^53-1，而非 19 位。两侧 id 都是精确字符串；冷、热原始 body 各 1289 字节、SHA256 相同，images:null 保留；三次顺序请求保存原件并核对 mapper SQL 为 2/0/1。不能把这说成已测试所有大 ID 或已证明 APP 前端接入。

## 排障与取舍

新增 VO 首轮因运行目录 model JAR 过旧触发 NoClassDefFoundError；刷新依赖又带回 logback 导致 ENV-003 复发，随后将 classpath 准备步骤脚本化。两个失败快照保留；这些是构建/运行产物问题，不能把业务码 503 当作接口已测成功。

保留 VO 在现有 model/article/vos，避免无收益的目录搬迁。修复后单轮 A/B 仅作观测，预热和采样计数分开；事务开销和稳定收益另测。

## 60–90 秒讲述草稿

> 我在核对详情接口时发现，同一个 ID 冷读是字符串，缓存命中后却成了数字。排查到两条路径用了不同的对象类型和序列化方式：冷读是实体，热读是 Map，只有前者经过项目的 id 字符串规则。我把两条路径统一成同一 VO 和 ObjectMapper。验证不只看页面或业务码，而是用超过安全整数范围的 ID 检查原始响应，再比较冷、热两个文件的字节和哈希，并用顺序请求的 SQL 日志确认读库与命中路径。这个实验解决的是 API 契约问题，不能据此认领整个 APP 的性能收益。

按本人实际参与复述，不将 agent 的操作改写成独立生产排障经历。

## 追问

- 为什么换 Map 会影响 ID？Map 的值序列化不等于 POJO 属性的 BeanSerializerModifier 规则。
- 为什么不用 JavaScript 先解析再判等？如果 ID 已按不精确的浮点数解析，断言本身也可能失真；用原始字面量或精确类型。
- 为什么字节一致仍不等于全功能通过？只覆盖给定样本和状态，补录、TTL、旁路更新、失败回源等仍需后续任务。
