# MQ-001：search 启动失败的处理器层级排查

类型：本地项目启动故障，已复现并修复；不是生产事故。执行由 agent 完成，用户独立复述/复跑状态：待确认。证据与版本见 [P0.1 负责人审阅](../20261029-P0.1-负责人审阅.md)。

## 现象和根因

search 在创建 syncArticleListener 时抛 BeanNotOfRequiredTypeException：注解 errorHandler 要求 KafkaListenerErrorHandler，实际 Bean 是 SeekToCurrentErrorHandler。外部依赖端口可连后仍有此栈，不能继续只从网络排查。

根因是两种处理器的挂载层级混淆：注解属性针对监听方法处理器，原配置对象针对容器。只把类名或接口换成能通过类型检查的实现，可能改变异常传播；本轮选择保留原对象和参数，纠正挂载位置。

## 修复与验证

移除注解的错误引用，用 Boot configurer 初始化容器工厂后挂载原 SeekToCurrentErrorHandler。两文件新增差异明确，其余 11 个受控文件哈希不变。编译成功；run04 上下文启动、51804 和分区分配有记录；只读探针核对容器使用原 Bean，并保留 FixedBackOff 和 recoverer。

探针前几轮按错误结构找字段输出 NOT_FOUND；随后用 javap 核对实际 2.6.6 类结构才取得参数。保留这些失败尝试，可以讲“版本约束下如何核实 API”，不能说第一次就找到了全部原因。

## 60–90 秒讲述草稿

> 在本地复跑资讯项目时，search 启动失败。我先把依赖连通和应用异常分开，原栈明确指出 Bean 类型不匹配。继续对照框架版本，发现注解要的是方法级处理器，而项目注册的是容器级处理器。我保留原重试参数和死信恢复器，通过 Boot 的容器工厂配置把它接到正确位置。验证时除了看启动成功，还从实际监听容器读取处理器，确认就是原 Bean。到这里能证明启动与接线修好了；重试次数、死信是否可靠、消息是否写入 ES，还需要后续单独注入故障验证。

此稿供理解后复述。个人参与按实际填写，不把 agent 的排查直接称为本人独立完成。

## 三层追问

- 为什么不能只看启动没有 ERROR？错误 Bean 引用删除后也可能落到默认处理器，需验证目标容器实际绑定。
- 为什么探针不证明重试可靠？它读取的是配置对象，未触发失败、offset 提交、恢复器投递或 DLT 失败路径。
- 升级后如何处理？按目标版本迁移错误处理 API，并重测异常传播、重试、offset、DLT 和消费者配置；不靠替换一个方法名认定语义相同。
