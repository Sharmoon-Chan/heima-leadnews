# P1.0 路由表与受控对照实现说明

日期：2026-10-29。阶段：P1.0（只做本卡，不进入 P1.1–P1.3）。
本文件记录**调用方 → 外部 URL → 服务 URL → SQL/cache** 的链路，以及 A/B 对照是怎么搭的。

## 1. 路由表（详情链路）

| 层 | 实际值 | 证据等级 |
|---|---|---|
| 前端页面 | **未核实**。仓库内没有前端代码（无 `.html`/`.js` 业务文件，也没有 portal 模块） | 未核实 |
| 网关外部 URL | `GET http://<gateway>:51601/article/api/v1/article/detail/{id}`，需 `token` 请求头 | **已实测**（2026-10-29 P0 复测：无 token 401；带 token 200/业务码 200） |
| 网关路由规则 | Nacos `leadnews-app-gateway`：`Path=/article/**` → `lb://leadnews-article`，`StripPrefix=1` | **已取得配置原文** |
| 服务内 URL | `GET /api/v1/article/detail/{id}`（`ArticleInfoController#detail`，article 服务端口 51802） | **已实测** |
| 服务方法 | `ApArticleServiceImpl#getArticleDetail(Long)` | 源码 |
| Redis key | `article:detail:{id}`（正常值），空值占位取值 `__NULL__`；锁 key `article:detail:{id}:lock` | 源码 + 实测 |
| SQL（回源） | ① `ap_article` 按主键查 1 行；② `ap_article_content` 按 `article_id` 查 1 行 | **已实测**（见第 4 节） |
| 首页列表（另一条路） | `POST /api/v1/article/load` → `ApArticleServiceImpl#load2`；热点列表缓存 key 由 `ArticleConstants.HOT_ARTICLE_FIRST_PAGE + tag` 组成；热点数据由 `ComputeHotArticleJob`（xxl-job）与 `HotArticleStreamHandler`（Kafka Streams 阅读数）生成 | 源码；**本轮未做请求验证** |
| 静态 HTML 详情 | `ArticleFreemarkerServiceImpl`（`@Async`）生成 → 上传 MinIO → 回写 `ap_article.static_url`，再发 Kafka 索引消息 | 源码；**本轮未触发**（P1.0 数据把 `static_url` 全部置 NULL，见第 3 节） |

**结论边界**：能证明的是「网关 → article 服务 → MySQL/Redis」这条 API 链路。**不能**说 APP 详情页整体受益——
前端调用方始终没有证据（CACHE-005 维持未核实），所以简历措辞只能是「详情 API」。

## 2. 为什么必须做同接口对照

同一个「文章详情」语义在本仓库里存在三条实现路径：

| 路径 | 数据来源 | 会不会用 Redis 详情缓存 |
|---|---|---|
| 静态 HTML（`static_url`） | MinIO 上的预生成文件 | 不会 |
| 首页/热点列表（`load2` + 热点缓存） | Redis 里的列表快照 | 不会（用的是另一个 key） |
| 详情 API（`/detail/{id}`） | Cache Aside：Redis → 未命中回源 MySQL | 会 |

三者的响应体、访问链路、负载模型都不同。拿「静态页 vs 动态 API」或「首页列表 vs 详情 API」比，测到的是链路差异，
不是缓存的收益。所以 P1.0 的主实验只有一条：**同一个 `GET /detail/{id}`，只切换「是否读写 Redis 详情缓存」。**

## 3. A/B 是怎么搭的（最小改动）

### 3.1 开关

`ApArticleServiceImpl` 新增字段：

```java
@Value("${article.detail.cache.enabled:true}")
private boolean articleDetailCacheEnabled;
```

- 默认 `true`，即正常 Cache Aside 行为；这是普通属性开关，没有 profile 硬限制。负责人接受保留，实验仅在 p1 启动配置中切换，不写成“其他 profile 无法关闭”；
- `false` 时：不读缓存、不抢锁、不写缓存、不写空值占位，直接走 `queryArticleDetail(id, null, false)` → 2 条 SQL；
- 该 key **故意不写进 Nacos**，因为 Nacos 属性源优先级高于命令行；不写它，才能用启动参数
  `--article.detail.cache.enabled=false` 切换（ENV-006 的教训）；
- 没有新增任何 HTTP 调试入口，正常返回结构不变。

### 3.2 打点

每个详情请求输出一行结构化日志：

```
[DETAIL-METRIC] reqId=<n> articleId=<id> mode=<CACHE|DIRECT> result=<HIT|NULL_HIT|DB_HIT|DB_MISS> \
                lock=<NONE|ACQUIRED|WAIT_THEN_HIT|WAIT_THEN_DB|DOUBLE_CHECK_HIT|DISABLED> dbSelect=<0|1|2> costMs=<n>
```

`dbSelect` 只统计本次请求真正发起的 DAO 调用（`getById` 计 1，正文查询计 1），因此：

| 场景 | result | dbSelect |
|---|---|---|
| 正常缓存命中 | `HIT` | 0 |
| 空值占位命中 | `NULL_HIT` | 0 |
| 回源命中 | `DB_HIT` | 2 |
| 回源未查到 | `DB_MISS` | 1 |

该字段是按业务分支记录的 DAO 调用数，本轮已在三次顺序请求用 SQL DEBUG 对照；它不是对所有并发/异常请求的实际服务端 SQL 计量。用日志而不是 `Redis INFO`，因为 `INFO` 的命中率是**实例级**的，混进了本接口之外的 key 和连接，
不能作为本接口指标（05 规范与 P1 卡都要求这一点）。

### 3.3 契约一致性（CACHE-006 公共修复，同时作用于 A/B）

- 冷读与热读都用 `ArticleDetailVo{article, content}`；
- 写缓存与读缓存都用**注入的 Jackson ObjectMapper**（即 HTTP 响应序列化用的同一个），不再用 fastjson 转 Map；
- 结果：`article.id` 在两条路径上都是字符串（项目 `ConfusionModule` 的约定），null/缺省策略也一致。

这条修复对 A 组同样生效（A 组也走 `ArticleDetailVo` 出参），所以 A/B 的**响应体和序列化成本相同**，
差异只来自「是否走 Redis」。

## 5. 已知混杂因素（不影响 A/B 同等性，但影响解读）

1. **类级 `@Transactional`**：`ApArticleServiceImpl` 是类级事务，`getArticleDetail` 也会开启事务并占用连接，
   即使在纯缓存命中路径上也是如此。A/B 两组都受同样影响，因此组间可比；但这意味着**B 组并未免掉连接池开销**，
   可能存在额外开销；没有去事务对照，不能确定其吞吐贡献或理论上限。属 P1.3 范围，P1.0 未改。
2. **压测端与服务同机**（同一台笔记本，16 逻辑核）：客户端占用会与 JVM 抢 CPU。
3. **闭环固定并发**：记录的是该并发下的观测值，不是容量结论；未做 AB/BA 交替三轮（P1.0 只要求小规模首份基线）。
4. 单机、单实例、Redis 无持久化；`article:detail:*` 与本机其他项目共用 db0（本轮只操作精确测试 key）。
