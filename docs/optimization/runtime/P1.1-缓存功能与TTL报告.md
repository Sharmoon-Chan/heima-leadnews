## 2. CACHE-HOT：正常命中 → TTL 过期 → 回源重填

run_id `20261029-P1.1-HOT-r02`，断言 **14/14 通过**（`CACHE-HOT/assertions.json`）。

| 步骤 | 请求前 key | HTTP | 业务码 | 响应字节 | 请求后 PTTL | 应用 metric | 声明 DAO 调用 |
|---|---|---|---|---|---|---|---|
| hot-1-cold | 不存在(`-2`) | 200 | 200 | 1289 | 14878 ms | `DB_HIT dbSelect=2` | 2 |
| hot-2-hit | 存在(14584) | 200 | 200 | 1289 | 14507 ms | `HIT dbSelect=0` | 0 |
| hot-3-after-expiry | **不存在(`-2`)** | 200 | 200 | 1289 | 14921 ms | `DB_HIT dbSelect=2` | 2 |
| hot-4-refilled-hit | 存在(14680) | 200 | 200 | 1289 | 14603 ms | `HIT dbSelect=0` | 0 |

结论（**有证据**）：

- 冷读回源并回填：请求后 key 存在、TTL≈15 s（`expire=15`、`jitter=0`）；
- 热读命中：请求前 key 存在，`dbSelect=0`；
- **TTL 到期确实回源**：hot-3 请求前 `EXISTS=0`、`PTTL=-2`，随后 `dbSelect=2` 并重新回填；
- 冷读 / 热读 / 过期后回填三次响应**逐字节相同**（1289 B，`-ceq` 通过），说明契约在过期重生后仍一致。

## 3. CACHE-NULL：空值占位 → 命中 → 过期 → 再次回源

run_id `20261029-P1.1-NULL-r02`，断言 **11/11 通过**（`CACHE-NULL/assertions.json`）。

| 步骤 | 请求前 key | HTTP | 业务码 | 响应字节 | 请求后 PTTL | 应用 metric | 声明 DAO 调用 |
|---|---|---|---|---|---|---|---|
| null-1-first-miss | 不存在 | 200 | **1002** | 70 | 7853 ms | `DB_MISS dbSelect=1` | 1 |
| null-2-null-hit | 存在(7513) | 200 | **1002** | 70 | 7388 ms | `NULL_HIT dbSelect=0` | 0 |
| null-3-after-expiry | **不存在** | 200 | **1002** | 70 | 7928 ms | `DB_MISS dbSelect=1` | 1 |
| null-4-null-hit-again | 存在(7660) | 200 | **1002** | 70 | 7572 ms | `NULL_HIT dbSelect=0` | 0 |

结论：

- 首次未命中写空值占位，TTL≈8 s（`null-expire=8`）；
- 重复请求同 ID 由占位拦住，**0 条 SQL**，业务码仍是 1002（不是 500、不是空页）；
- 空值到期后再次回源（1 条 SQL），并重新写占位；
- 四次响应逐字节相同（70 B）。

## 4. TTL 抖动窗口

run_id `20261029-P1.1-JITTER-r02`（`expire=20`、`jitter=10`），断言 4/4（`JITTER/assertions.json`）。
12 个不同 ID 冷读后立即读 `PTTL`：

| 指标 | 值 |
|---|---|
| 最小 TTL | **19.9 s** |
| 最大 TTL | **28.9 s** |
| 不同取值个数 | **7** |
| 预期区间 | `[20, 30)` 秒 |

样本：24.9 / 21.9 / 27.9 / 21.9 / 21.9 / 28.9 / 19.9 / 27.9 / 22.9 / 21.9 / 22.9 / 23.9（秒）。
这些观测与抖动生效一致。PTTL 是设置后的剩余寿命，19.9s 可由期间耗时消耗解释，不是 PTTL 自身按秒取整；剩余样本不等于初始设置 TTL，12 个样本也不证明随机分布质量。

## 5. 大量随机新 ID：空值缓存**不能**拦住从未访问过的 ID

run_id `20261029-P1.1-RANDOMNEW-r03`，断言 4/4（`RANDOMNEW/assertions.json`）。

| 批次 | 规模 | 行为 | 结果 |
|---|---|---|---|
| A 第一遍 | 20 个全新不存在 ID | 每个都回源 | 全部 200/1002，**每个都写了占位** |
| A 第二遍 | 同上 20 个 | 请求前占位均存在 | 全部由缓存拦住，`dbSelect=0` |
| B | 200 个从未请求过的新 ID | 每个首次触碰 | 全部 200/1002，**每个都回源一次** |

按时间窗从应用日志归属本次运行（240 次请求）：

```
result 分布:  DB_MISS 220 / NULL_HIT 20
dbSelect 合计: 220  =>  平均 0.9167 次声明 DAO 调用/请求
```

**结论（这是本卡要求单列的部分）**：空值缓存只对「同一个不存在 ID 被重复请求」有效；
对持续涌入的新 ID，每个新 ID 仍要 1 次回源。因此不能用它宣称「挡住了全部穿透流量」。

## 6. 补录与写入口失效

run_id `20261029-P1.1-BACKFILL-r05`，断言 **12/12 通过**（`BACKFILL/assertions.json`）。
测试 ID `9007199254760090`（原本不存在）。实验结束后该行已从测试库删除（`ap_article` 回到 10000 行）并删除对应 key。

| 步骤 | 做了什么 | 观测 |
|---|---|---|
| b0 | 查询不存在 ID | 200/1002，写入 `__NULL__` 占位 |
| b1 | **绕过服务**直接 SQL 插入同 ID 的行 | 行确实在库里（`count=1`），但再次查询**仍返回 1002** —— 占位没被清 |
| b2 | 通过服务 `POST /api/v1/article/save`（dto.id 相同）写入 | 调用后 key **立即不存在**（`EXISTS=0`）；再查询 → **200**，新内容 `backfill body v2` 可见 |
| b3 | 等 8 s 看异步静态化是否更新 `static_url` | 仍为 `NULL`：异步链路在本轮**失败**（见 6.1） |
| b4 | 用代码里同一句 `UPDATE ... SET static_url` 模拟该写路径，再查详情 | 库里 `static_url` 已更新，但**详情接口仍返回 `staticUrl:null`** —— 缓存未失效 |

### 6.1 静态化链路本轮为什么没跑通

`ArticleFreemarkerServiceImpl.buildArticleToMinIO` 是 `@Async`，日志：

```
ERROR ... SimpleAsyncUncaughtExceptionHandler : Unexpected exception occurred invoking async method
java.lang.RuntimeException: 上传文件失败
    at com.heima.file.service.impl.MinIOFileStorageService.uploadHtmlFile(MinIOFileStorageService.java:106)
```

原因是我在 `p1` profile 里填的是占位 MinIO 凭据（`minioadmin`），VM 上的 MinIO 不接受，上传失败 →
`static_url` 从未被真实链路写入。**所以 b3 只能证明「异步链路没跑通」，不能证明「跑通后会失效」**；
b4 是对**同一句 UPDATE** 的模拟，已在文件中明确标注为模拟，不冒充 freemarker 链路。
修 MinIO 凭据属于环境配置，本卡未做（避免往共享 Kafka/ES 里泼测试消息），已单列为遗留项。

## 7. 参数候选表

| 参数 | 单位 | 代码默认（原值） | 本轮试验值 | 依据/说明 | 选择 |
|---|---|---|---|---|---|
| `article.detail.expire-seconds` | 秒 | 1800 | 15 / 20 | 原值保留为候选；缩短值只作功能验证 | **维持 1800**，待 P4 综合复测 |
| `article.detail.expire-jitter-seconds` | 秒 | 300 | 0 / 10 | 抖动区间 `[0, jitter)`；实测 12 个 key 分布 19.9–28.9 s | **维持 300** |
| `article.detail.null-expire-seconds` | 秒 | 60 | 8 | 决定「补录可见性」的最坏窗口；外部写入未失效时，最多被挡这么久 | **维持 60**，但见下方风险 |
| `article.detail.cache.enabled` | 布尔 | true | — | P1.0 引入的对照开关，默认 true | 维持 |

取舍说明（本卡要求写清）：

- **TTL 不是严格陈旧上界**：没有旧回源重写/后续变更时，到期可重新查询；并发回源、事务快照和失效失败会改变窗口，不能说任意情形最多一个 TTL。
- **空值 60 s**：本轮只证明更新分支样本清占位，外部插入未清；未证明所有新增/并发补录都立即或严格 60s 可见。
- 内存占用：单 key 约 1.2~1.3 KB（实测 `STRLEN=1227`、响应 1289 B）；1 万热文章 ≈ 12 MB 量级，
  仅为 value 载荷，不含 key/对象/字典/过期索引/碎片，未测实例总资源，不能由此判定内存不是瓶颈。
- 命中率：本轮功能试验的命中率（≈99.7%，P1.0）**包含预热**，不能当稳态指标；正式命中率需按 05 规范的多轮采样。
