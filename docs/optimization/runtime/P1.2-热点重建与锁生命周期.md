## 2. 修前的两个缺陷（原件）

### 2.1 CACHE-001 固定值锁被旧持有者删除（C3）

run_id `20261030-P1.2-C3-PRE-r04`（主 41372 / 持有者 33128）。

```
A(51803) lock.acquired  t≈147ms      lockValue=1 leaseMs=3000
        lease 到期     t≈3274ms      EXISTS=0（A 仍在临界区内，taskA.IsCompleted=False）
B(51802) lock.acquired  t≈3350ms     新锁 EXISTS=1 PTTL≈2916（值同样是 "1"，无法区分持有者）
A 返回 200，finally 执行 release      t≈4000ms  mode=delete_without_owner_check
        → 采样：EXISTS=0             ← B 仍持有，但它的锁被 A 删掉了
B 返回 200，finally 执行 release      → 已无锁可删
```

判据：`c3.B_lock_survived_A_finally` = fail（exists=0），即**旧持有者的 finally 删除了新持有者的锁**。原件：`runs/20261030-P1.2-C3-PRE-r04/`（`scenario-result.json`、`samples`、`events-holder.log`、`events-main.log`、两个响应体）。

### 2.2 CACHE-002 50 ms 后无约束回源放大（C2）

修前 `pairs-preA.csv`，同一冷 key、同步起跑：

| 组合 | 轮次 | 请求 | 成功 | 拒绝 | 回源尝试 | 峰值并发回源 | p95 |
|---|---|---|---|---|---|---|---|
| C2 并发 10 | 3 | 30 | 30 | 0 | **30** | **10** | 435 ms |
| C2 并发 30 | 3 | 90 | 90 | 0 | **90** | **30** | 517 ms |

即 9/29 个等待者在固定 50 ms 后各自查库，回源并发等于请求并发。事件里可见 `lock.fail → wait.end outcome=no_lock_then_db`。C1（回源约 10 ms < 50 ms）修前已经是 1 次回源，说明放大只在「重建时间 > 固定等待」时出现。

## 3. 修复内容（最小）

1. **所有权令牌**：锁值由固定 `"1"` 改为 `UUID`。
2. **原子释放**：`CacheService` 只新增一个窄方法 `releaseIfValueEquals(key, expected)`，用 Lua
   `if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end`，
   **不做先 GET 后 DEL**；未改变任何既有方法。
3. **有界等待**：未获锁时循环「重查缓存 → 按剩余预算退避（10 ms 起、50 ms 封顶、加抖动）→ 重新争锁」，
   预算用单调时钟 `System.nanoTime()`；预算耗尽 → 业务码 503 且结构化结果标记 `FAIL_WAIT_BUDGET_EXHAUSTED`。
4. **失败分类**：读缓存/争锁/释放的 Redis 异常分别标记 `FAIL_REDIS_ERROR_LOCK`、重查失败、
   `release.error`；中断标记 `FAIL_INTERRUPTED`。都不降级成无锁回源。
5. **配置**：`article.detail.lock.expire-millis`(3000)、`wait-budget-millis`(1000)、
   `wait-backoff-millis`(10)、`wait-backoff-max-millis`(50)；启动自检：非正数回退默认并 WARN，
   预算 ≥ 租期时收敛到租期一半。

### 4.3 预算不足时的显式失败（不靠拒绝冒充优化）

把预算改成 200 ms（< 300 ms 慢回源），并发 10，run_id `20261030-P1.2-C2-POST-budget200-r01`：

```
成功 1（持有者）、显式 503 9、回源尝试 1、峰值回源并发 1、wait_outcomes={budget_exhausted:9}
锁争抢尝试 45 次（9 个等待者 × 预算内重试）
```

即：**DB 压力降低并不总是伴随拒绝**——预算够（1000 ms）时是「1 次回源 + 全部成功」；预算不够（200 ms）时是「1 次回源 + 9 个明确失败」。两种取舍都记录，不把被拒绝的请求算成同一份成功流量。

### 4.5 C5 Redis 异常（模拟）

三个独立实例，各自用故障配置启动（只影响该实例，**没有停止 Windows Redis**）：

| 阶段 | run_id | 结果 |
|---|---|---|
| 读缓存 | `C5-READ-r01` | HTTP 200 / 业务码 **503**，`fault.redis.injected stage=read` 一次，未回源 |
| 争锁 | `C5-LOCK-r01` | HTTP 200 / 业务码 **503**，`stage=lock` 一次，未回源 |
| 释放 | `C5-RELEASE-r02` | 原请求结果**保留**（200 + 精确 ID），`release.error` 留痕；残留锁 `EXISTS=1 PTTL≈2788`，只能等租期回收 |

审阅纠正：读/争锁注入实际仍到未捕获异常的全局 ExceptionCatch，再返回业务 503；不能沿用“未捕获异常路径不再被走到”或据此认为具体分类分支通过。释放失败保留结果样本有效；残留锁依赖租期，不声称故障下线性一致。

### 4.6 C6 等待线程被中断

run_id `20261030-P1.2-C6-POST-r05`。先等 A 真实持有锁（`c6.holder_holds_the_lock_before_waiter_starts`），再发 B：

```
B lock.attempt attempt=1 → lock.fail
B wait.pre_sleep  attempt=1 sleepMs=20 threadInterrupted=false cfgInterrupt=true
B interrupt.injected phase=before_sleep attempt=1
B wait.end        outcome=interrupted attempts=1
B 响应 503（未成功）、该请求 db.enter=0
```

7/7 通过。**两处必须说明**：

1. 中断用夹具注入到「即将 sleep」的线程（该线程此刻确定在等待循环内），不是靠断开 HTTP 连接推断服务端中断。
2. 代码**清除**中断标记而不是重新置位，这一点与卡面字面要求不同。原因是实测：把标记留给容器后，Tomcat 写响应时抛
   `java.io.IOException: The current thread was interrupted`，栈在 `SocketWrapperBase.doWrite → flushBlocking`（原始
   日志 `logs/fixed/fixed-main-r01.log` L699–L710：先出现探针写事件失败 `ClosedByInterruptException`，随后
   `ExceptionCatch` 记录该 IOException，客户端收到断流）。中断事实已写入结构化结果（`outcome=interrupted`、
   `FAIL_INTERRUPTED`），不构成吞掉信号。C6 首轮 `C6-POST-r02` 的失败就是这一现象的原始记录。

## 5. 对账口径

- **回源尝试** = `event=db.enter` 的次数（每次 `getById` 一次 DAO 进入）。这是 DAO 调用级，不是物理 SQL 数；
  真实 SQL 会因 `getById` + 正文查询变成 2 条，本轮没有做逐请求物理 SQL 归属，因此不写成「SQL 数」。
- **峰值并发回源** = 所有 `db.enter`/`db.exit` 按 `epochMs` 形成的区间求最大重叠，跨进程合并（按 pid 区分），
  不是单 JVM 计数器。
- **等待结果** 来自 `wait.end outcome=hit|budget_exhausted|interrupted`；**锁结果** 来自 `lock.acquired`/`lock.fail`；
  **释放结果** 来自 `release deleted=0|1` 或 `release.error`。
- 客户端延迟分位数用采集脚本的 `Stopwatch`，**包含**排队与等待预算，不等同服务端处理时间。
- 每次请求都独立落盘（`wNNN.body.json` + `requests-meta.json`），断言从文件回读；同步性另用服务端
  `request.start` 的时间跨度校验（`burst.arrived_together`，本机 30 并发实测 5–150 ms）。

## 6. 三个必须报告的边界

1. **循环预算 ≠ 整个请求的时限**。预算 1000 ms 只在两次 Redis I/O 之间检查；单次 Redis 命令超时是
   `spring.redis.timeout=2000ms`，所以极端情况下单次 I/O 就可能超过预算。客户端 HTTP 超时另设（突发脚本 30 s、
   生命周期脚本 90 s），大于任何预算，因此不会用客户端超时掩盖服务端仍在等待。采集结束前会等后台请求收敛
   （按 `db.enter`/`db.exit` 未闭合判断）。
2. **类级 `@Transactional` 让连接池成为并发上限**。修前用默认池（10）跑 30 并发时，只有 10 个请求能进入业务方法
   （服务端 30 个 `request.start` 跨 397 ms，回源并发峰值 10）——这就是「等待者先占 DB 连接」的实测影响。
   为让 10/30 并发都真正成立，本轮把 Hikari 上限提到 40，**修前修后相同**，并在交接中记录；
   事务拆分本身仍留 P1.3（CACHE-003）。DB/连接池等待时间未单独测量，只记录该上限效应。
3. **令牌只防「旧持有者删新锁」，不提供严格互斥**。没有续租，持锁方超过租期仍可能有第二个回源者；
   过期持有者回填缓存也不由释放 Lua 解决。本轮没有验证「任意并发下最多一个 TTL 的陈旧」这类断言。

## 9. 第二轮复验边界（2026-10-31）
