## 3. T1 事件对账（同一查询口径）

选取规则：写方按 `requestId=writer`；读方按 `requestId=reader-during-tx`；删除与提交按 `epochMs` 全序比较。

PRE：

```
1793418983352  event=cache.evict.begin  phase=PRE:inTransaction
1793418983352  event=cache.evict.ok     phase=PRE:inTransaction
1793418983352  event=cache.evict.second_scheduled delayMs=500
179341898385x  event=cache.evict.second_begin     (定时线程, runId=-)
1793418985xxx  reader: cache.read hit=false → db.enter → setEx(V0)
1793418986372  event=tx.hold.end
(此后 COMMIT；客户端在提交后返回 200)
```

POST：

```
1793418798xxx  event=cache.evict.register reason=saveArticle:update inTransaction=true txActive=true syncActive=true
1793418798xxx  event=tx.hold.begin holdMs=3000
1793418799xxx  reader: cache hit(V0) → 响应 V0（提交前的可见值）
1793418801xxx  event=tx.hold.end
1793418801557  event=tx.after_commit reason=saveArticle:update txActive=true
1793418801558  event=cache.evict.begin  phase=saveArticle:update:afterCommit
1793418801558  event=cache.evict.ok
1793418801558  event=cache.evict.second_scheduled delayMs=500
(之后 detail 重新回源，读到 V1)
```

说明：两次运行的 hold 都是 3000 ms，因此 `tx.hold.end` 落在 `tx.hold.begin + 3000`；`tx.after_commit` 与首次 `cache.evict.ok` 只差 1 ms，属于同一毫秒级相邻。PRE 与 POST 的绝对毫秒值来自各自运行，**不能跨运行相减**；能比较的只有同一次运行内部的先后：PRE 的删除早于 `tx.hold.end`，POST 的删除晚于 `tx.after_commit`。

## 4. 连接占用证据

- 采集点：`GET /p13a/harness/stats`（实验 harness），字段 `conn_active/conn_borrows/conn_returns`，由只观测的 `DataSource` 包装计数（`close()` 已真正归还连接后计数）。
- 缓存命中：请求约 2 ms，采样窗口抓不到峰值，因此用**借用计数差值**：PRE `+1`、POST `+0`。
- 锁等待（预算 1000 ms，外来锁 `PX 4000`）：PRE 期间最大活跃连接 `1`（14 次采样），POST `0`（14 次采样）；两者业务码都是 503（预算耗尽，符合 P1.2 失败策略）。
- 短读事务：`db.snapshot.begin` … `db.snapshot.end` 成对出现（POST 6 条事件 / 3 次回源），PRE 没有该事件（整段请求都在类级事务内）。

## 5. 已知偏差与风险

1. **500 ms 窗口外的回填仍会留下脏缓存**（T3 窗口外样本）。这是既有策略的残余窗口，本卡不修、不选参。
2. **延迟删除仍是单机线程池**：进程重启会丢失未执行的第二次删除（P1.3c）。
3. **共享Redis与多实例**：afterCommit在写实例执行，但DEL对其他实例后续读取同一Redis key同样可见。未验证的是多进程竞态、故障及单机延迟任务丢失，不推断存在独立本地缓存。
4. **T4 的无事务分支**由 harness 直接调用失效器验证，`saveArticle` 本身总是带事务；因此 T4 不证明 `saveArticle` 在无事务环境下的行为。
5. `fault.cache.evict=once` 的「一次」是**进程内**语义：同一实例第二轮不会再注入（已按新进程重跑，见交接 §7）。
6. 连接计数包装是实验 harness 的一部分，**不在仓库源码**；生产路径不使用它。

代表实例46028不是所有场景PID；T1-r03实际13180。首轮读取隔离级别未实测；后续已在 §6.3 取得实际连接 RR 证据，不能倒填成首轮已取证。固定3000ms停顿结合实际日志证明本次顺序，不称严格可释放屏障。

### 6.3 T6 短读事务的真实身份（`P13a-POST-T6-r08`，请求 `requestId=cold`）

```
phase=before_first_select txActive=true readOnly=true resourceBound=true resourceId=7cc3ccb5 connId=19012e9f isolation=4 autoCommit=false
phase=after_second_select txActive=true readOnly=true resourceBound=true resourceId=7cc3ccb5 connId=19012e9f isolation=4 autoCommit=false
```

- `resourceId` 相同 → 两条 SELECT 共用同一事务资源；`connId` 相同 → 同一连接对象（identity hash）。
- `isolation=4` 是连接的**真实** JDBC 隔离级别（`REPEATABLE_READ`），`autoCommit=false` 表示事务已接管提交；两者都由 `Connection` 直接读出。
- 冷读后 `conn_active=0`：短读事务返回即归还连接，随后才 `cache.write.done` 回填。
- PRE 对照 `tx.trace` = 0 条（没有短读事务）。

### 6.4 正常等待命中（`P13a-POST-T6-r08`）

```
holder-slow : 先拿到锁（db.delay=600ms）
waiter-hit  : lock.fail ×10 → lock.acquired(attempt=11) → recheck_after_lock 命中 → release(deleted=1)
              http=200 biz=200 title="P1 article 14" elapsed=662.9ms  "id":"9007199254741014"
              waiter 的 db.enter/rebuild.begin = 0；等待期 conn_active 采样 9 次峰值 0
```

判定键写的是实际路径 `post_lock_double_check(DOUBLE_CHECK_HIT)`。等待循环内部的 `wait.end outcome=hit` 需要「持有者已写缓存但未释放锁」的窗口，该窗口在现有实现里是微秒级，本轮没有确定性采到，**不声称覆盖该分支**；原预算耗尽 503 样本（peak 连接 0）保留。
