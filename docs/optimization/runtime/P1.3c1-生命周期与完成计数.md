## 1. 组件现在的样子

`DetailCacheInvalidator`（`com.heima.article.support`）：

- 一个 `ScheduledThreadPoolExecutor`，**单线程**、线程名 `p13a-cache-evict`、daemon；延迟仍为 **500ms**。
- 关机策略显式设置：`setExecuteExistingDelayedTasksAfterShutdownPolicy(false)`、`setContinueExistingPeriodicTasksAfterShutdownPolicy(false)`、`setRemoveOnCancelPolicy(true)`。含义：`shutdown()` 之后**不会再执行已排队的延迟任务**，这些任务由本组件统一计为取消。
- 实现 `DisposableBean`，`destroy()` 就是 Spring 关闭钩子。
- 一把 `stateLock` 统一协调「接受/发布 → 开始 → 终态 → 关闭/取消」；`task_id` 用进程级静态序列，`t<pid>-<全局序号>`。
- 关闭等待窗口 `p13c.evict.close-wait.ms` 是**组件范围**工程配置（缺省 2000ms，不是压测选参）；按精确 articleId 且缺省关闭的夹具是 `fault.cache.evict.second.<id>`（只打第二删）与 `slow.cache.evict.second.<id>`（第二删停顿）。

## 2. 一个第二删任务的生命周期

```
提交（全部在 stateLock 内）
  submitAttempts++
  closing? ──是──▶ rejected_closed，结束（不登记、不调度）
        │否
  activeTasks.put(taskId=t<pid>-<进程级序号>, QUEUED)      ← 先发布
  schedule(...)  ──抛异常──▶ 撤回登记 + rejected_scheduler（不算接受）
  accepted++；写 second_scheduled / second_accepted
        │
        ▼ (≥500ms 后由工作线程取出)
  stateLock: QUEUED? ──否（已取消/已终态）──▶ 直接返回，不复活
  QUEUED → RUNNING（记 started）
        │
  second_begin（锁外发出，因此一定晚于 accepted 事件）
        │  ┌── 可选受控停顿（slow.cache.evict.second.<id>，只对本轮 ID）
        ▼
  delete(key) 返回 ──▶ finish()：在 stateLock 内改状态 + 计数 + 移出活跃表 + 写终态事件

关闭（destroy）：
  ① stateLock 内：closing=true；记 queued/running 快照；写 shutdown_begin；shutdown()
     （此后提交一律拒绝；刚入队、尚在交接中的任务也一定被接手）
  ② 锁外：awaitTermination(close_wait_ms)      ← 持锁会阻塞运行中任务写终态
  ③ stateLock 内：对仍 QUEUED 的任务，
       cancel(false) 成功 | future.isCancelled() | 执行器已 terminated → CANCELLED
     其余（等待到期仍在运行）保持 RUNNING，交给它自己写终态；写 shutdown_end 回执
```

要点：发布先于调度，`RUNNING`/取消/终态都走同一把锁，因此「先执行后发布」「终态被写回活跃表」「关闭漏掉交接中的任务」三种倒序都不可能发生。等待到期仍在运行的 I/O **不被中断**，`destroy()` 返回时它仍是 RUNNING，之后由它自己写终态；关闭回执不会替它宣布成功或失败。

## 3. 事件与字段

探针事件（`events.file`）：`cache.evict.second_scheduled` 与 `second_accepted`（均已带 `taskId`）、`second_begin`、`second_pause_begin/end`、`second_succeeded` / `second_failed` / `second_cancelled`、`second_rejected`（`reason=closed|scheduler`）、`second_cancel_pending`、`shutdown_begin` / `shutdown_end`、`cache.evict.begin/ok/fail`（第二删时带 `taskId`）。

`/p13b/harness/stats` 的 `evict` 字段分四组：
- 原有兼容字段（9 个，含 `no_transaction_runs`）
- P1.3c-1 累计计数：`submit_attempts` / `accepted` / `rejected` / `rejected_closed` / `rejected_scheduler` / `started` / `succeeded` / `failed` / `cancelled`
- 当前数量：`queued_now` / `running_now` / `active_now`
- 关闭回执：`closed` / `close_finished` / `close_wait_ms` / `close_waited_ms` / `close_terminated` / `close_queued_before` / `close_running_before` / `close_cancelled` / `task_id_prefix`

所有 `*_ms` 单位毫秒，其余为次数。口径：`submit_attempts = accepted + rejected`；静止时 `accepted = succeeded + failed + cancelled`，`active_now = 0`。

## 6. 竞态夹具说明（不要把门控当成 mock 执行器）

`P13c1RaceProbe.GatedExecutor` 是**真的** `ScheduledThreadPoolExecutor` 子类，只重写 `schedule()`：入队后、返回前，若已 arm 则阻塞**提交线程**（有 5s 上限）。任务仍由真实 worker 执行，关闭仍走真实 `AnnotationConfigApplicationContext.close()`。反射替换的只是未被交付源码暴露的字段，业务 class 未改。Redis 出口 `RecordingCacheService` 只记录 `delete(key)`，不连 Redis。

## 7. 已知限制

- 只保证本进程内、本组件拥有的调度器；跨进程、SIGKILL、崩溃无补偿。
- 队列无上限；`shutdown` 后的排队任务计取消，不是“稍后补删”。
- 500ms 未调参；没有窗口/候选比较、没有容量/QPS 结论。
- 离线 L1–L4 与 A/B/C 的 Redis 出口是替身，真实 Redis 只在 L5 出现。
- 运行中如果 Nacos 注册失败，Spring 会关闭整个上下文：那时的 `详情缓存失效器关闭` 日志是真实关闭钩子，不是本卡引入的行为（见 TOOL-011）。
