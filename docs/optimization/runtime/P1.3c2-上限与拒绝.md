stats 新增三个字段，旧九字段保留：

```
delete_attempts, delete_failures, second_delete_scheduled, second_delete_done,
second_delete_failures, after_commit_runs, no_transaction_runs, rollback_skips,
second_delete_delay_ms                     <-- 旧九字段，一个都没少
```

恒等式（Q1/Q2/Q3/Q5 实测均成立）：`submit_attempts = accepted + rejected`；`rejected = rejected_closed + rejected_scheduler + rejected_backlog`；收敛后 `accepted = succeeded + failed + cancelled`。

## 2. 拒绝事件长什么样

```
ts=2026-11-03T16:45:21.812+0800 epochMs=1793695521812 pid=31700 thread=http-nio-51819-exec-6
runId=P13c2-Q5b-app-r01 requestId=P13c2-Q5b-app-r01-write-second event=cache.evict.second_rejected
reqId=0 articleId=9007199254743096 taskId=t31700-2 phase=updateScore:afterUpdate:afterCommit
reason=backlog maxActive=1 active=1 peak=1 key=article:detail:9007199254743096
```

- 拒绝发生在**第一删已经执行之后、提交之后**，所以写结果不受影响。
- `reason` 只有三种：`closed`（关闭中）、`scheduler`（执行器拒绝）、`backlog`（本卡新增的上限拒绝）。
- 归属靠 `articleId` + `taskId`（`t<pid>-<seq>`），不靠时间窗。

## 4. 应用回归（真实 HTTP / 事务 / DAO）

两个实例都由唯一入口 `start-p13b-instance.ps1` 启动，都在 51819、Redis DB5、`POST` 变体、`--article.p13a.harness.enabled=true`：

```

... -Tag P13c2-Q5a-POST-r03 -ProbeConfig <run>/configs/p13c2-probe-q5a2.properties
# 受控超限
... -Tag P13c2-Q5b-POST-r01 -ProbeConfig <run>/configs/p13c2-probe-q5b.properties `
    -ExtraSpringArgs '--article.p13a.harness.enabled=true --p13c.evict.max-active=1'
```

两个探针配置都在运行根内，`events.file` 也在运行根内：

- `p13c2-probe-q5a2.properties`：`events.file=<run>/events/p13c2-q5a2-app.log` + `p13b.rollback.updateScore.9007199254742094=true`
- `p13c2-probe-q5b.properties`：`events.file=<run>/events/p13c2-q5b-app.log` + `slow.cache.evict.second.9007199254743095=2500`

场景脚本：

```
powershell -File benchmarks/verify/p1-3c1-regression.ps1 -RunRoot <run> -RunId P13c2-Q5a-app-r02 `
  -Base http://127.0.0.1:51819 -Events <run>/events/p13c2-q5a2-app.log `
  -CommitId 9007199254742093 -RollbackId 9007199254742094        # 20/20

powershell -File benchmarks/verify/p1-3c2-limit-app.ps1 -RunRoot <run> -RunId P13c2-Q5b-app-r01 `
  -Base http://127.0.0.1:51819 -Events <run>/events/p13c2-q5b-app.log   # 21/21
```

两个脚本都是「写前 mysqldump 捕获 → 跑 → 按捕获 DELETE + 重放 INSERT → 逐行核对」，DB0 从不写、从不 FLUSHDB，只删本次写入的精确 key。

受控超限样本的关键时序：提交 `…3095`（第二删 2500ms）→ 200ms 后提交 `…3096` → 此刻 `active=1` 已占满 → 第二次提交照常提交、第一删照常执行、第二删被 `reason=backlog` 拒绝。

## 8. 边界

- 上限是**进程内组件状态**，不是分布式配额；多实例、SIGKILL、机器崩溃后没有跨进程补偿。
- 满载时被拒的是**第二删**，不是写请求；写路径与公开响应完全不变。
- 未调 500ms、未改线程数/执行器类型/锁/事务；不报容量、QPS、命中率或选参结论。
- 离线套件的 Redis 出口是替身；Redis 真实行为只在应用样本中出现。
