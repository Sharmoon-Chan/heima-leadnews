## 2. 读者与写者怎么造出窗口

- 读者 = 真实详情接口。`cache.write.delay.<articleId>` 的调用点在 [ApArticleServiceImpl](/D:/Code/Java/heima-leadnews/heima-leadnews/heima-leadnews-service/heima-leadnews-article/src/main/java/com/heima/article/service/impl/ApArticleServiceImpl.java:704)：`db.snapshot.end` 之后、`cache.write.begin`/`setEx` 之前停顿，所以快照是**真实旧值**，回填时间可控。
- 写者 = 真实 `updateScore`（`/p13b/harness/score`，四字段 +1、真实事务）。+1 而非更大增量，是为了避开静态化 worker 的独立删除干扰。
- 时序控制**不靠 sleep**：先发读者请求 → 轮询事件文件直到出现 `requestId=<本轮读者> … event=cache.write.delay.begin` → 此时才发写请求。因此「回填晚于提交」是真实发生的事实，不是计划出来的。
- 分类只看四条事件的实际 `epochMs`：`cache.write.delay.begin`、`tx.after_commit`、`cache.write.done`、`cache.evict.second_succeeded`。

## 4. 实际时间线（`P13c3-WINDOW-r02`）

W1-r1（300ms 停顿）：

```
delay.begin ──(+? )── commit ──(+245)── cache.write.done ──(+267)── second_succeeded
                                                                   ↑ 第二删把 V0 删掉
之后 3 次新读 → views=21678 = 库值（V1），stale 0/3
```

W2-r1（1500ms 停顿）：

```
delay.begin ──(+?)── commit ──(+506)── second_succeeded ──(+935)── cache.write.done
                                            ↑ 第二删已成功（此时 key 不存在）
                                                                  ↑ 之后才把 V0 写回
之后 3 次新读 → views=51317（库 51318）stale 3/3，TTL 1800 → 1799 → 1799，key 内 views=51317
```

六轮的完整数字在 `runs/P13c3-WINDOW-r02/window-result.json` 的 `rounds[]`：每轮都带 `times`（四条事件时间与三个差值）、`reader`/`writer` 响应、`db_before`/`db_after`、`second_delete` 计数、`new_reads[]`（含 `at_ms`、`views`、`stale`、`ttl_before/after`、`key_views`、`sha256`）。

## 5. 断言与原件

- 44 项断言逐条在 `runs/P13c3-WINDOW-r02/window-checks.tsv`。

## 8. 边界

- 只测固定 500ms；不报候选延迟、不报容量/QPS。
- W2 的「≥1.0s 陈旧 + 1800s TTL」是**观察下界**，不是过期时间或固定上限的证明。
- 单实例、单读者 + 顺序写者；跨进程/崩溃/并发多写者未覆盖。
