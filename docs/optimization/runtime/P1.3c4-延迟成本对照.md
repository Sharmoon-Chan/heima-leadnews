## 10. B 最终留存补修：读者共享方式与完成时刻落盘（2026-11-03）

### 10.1 读者为什么必须换共享方式

```
写侧  New-P13c4RequestLedger
        FileStream(path, Create, Write, FileShare.ReadWrite)   <- 整轮一直打开
读侧  Read-P13c4LedgerLines（最终版）
        FileStream(path, Open,   Read,  FileShare.ReadWrite)   <- 兼容上面的写句柄
读侧  Read-P13c4LedgerLines（上一版，已被重复定义覆盖）
        [System.IO.File]::ReadAllText(...)  -> 默认 FileShare.Read  -> sharing violation
```

PowerShell 里同名函数**后定义的覆盖先定义的**，所以上一版实际生效的是 `ReadAllText` 那份；「写流仍打开时读回」这条检查因此必然失败（负责人独立 10/13）。补修删掉重复定义，只留一份 `FileStream(Open, Read, FileShare.ReadWrite)` + UTF-8 + 5×20ms 重试；写侧的 `Writer.Flush()` / `Stream.Flush(true)` 未改。

另一处相关缺陷：`persisted_ms` 原来只在内存里，行内没有，于是「`persisted >= ended`」这类审计恒不成立。现在它在序列化**之前**写进行内，`flushed_ms` 只留内存。

### 10.2 异步慢读的时序：从 dispatch 到 completion 就落盘

```
dispatch          客户端完整响应           落盘                  下一条 sample
   |                    |                   |                        |
   t0                 t1 (ended_ms)       t2 (persisted_ms)        t3
   |------- elapsed_ms = t1 - t0 ------|
                      |--- lag = t2 - t1 ---|     必须 < 150ms，且 t2 < t3
```

- `Start-P13c4AsyncGet` 在 `SendAsync` 前记 `dispatched_ms`；`SendAsync` 默认 `ResponseContentRead`，任务完成即**正文收全**。
- `Complete-P13c4Get` 在采样循环里被**反复调用**（3ms 切片轮询）：一旦看到任务完成，立刻建记录（`started_ms = dispatched_ms`、`ended_ms = completion`）并 flush 到盘，才允许下一次 dispatch。
- 上一版的 `Finish-AsyncGet` 只在采样循环结束后才 Add，`ended_ms` 记的是收集时刻：负责人私有实证至少晚 642ms，期间还多发了 3 个采样。
- 记录写入由 `Monitor` 串行化；同一记录第二次 Add 直接抛 `ledger: record was already persisted once`，所以「一请求一次」由代码保证，不是事后数行数。

### 10.3 检查口径的变化（收紧，不是放宽）

| 检查 | 上一版实际含义 | 现在验证的内容 |

## 12. 2026-11-04 B 异步剩余补修：阻塞期也推进留存，完成时刻改夹逼（实跑）

### 12.1 等待方式：唯一入口 `Send-P13c4Responsive`

```
旧的 Send-Once
  SendAsync(req).GetAwaiter().GetResult()        <- 整段阻塞；这期间完成的 tracked 慢读不落盘

现在的 Send-Once（以及 Wait-Event 采样循环）

  while (-not task.IsCompleted) {
      Update-P13c4Tracked    -> 已完成的立刻建记录 + Flush；未完成的只刷新 last_incomplete_ms
      task.Wait(3)           -> 3ms 片
  }
  Update-P13c4Tracked        -> 收尾再服务一次
```

`Update-P13c4Tracked` 是唯一决定「谁落盘」的地方，它只服务在途请求本身；观察者（离线测试里是**独立进程**）只读文件记录「首见时刻」，不写任何记录。

### 12.2 四个时刻分开，真实完成用夹逼区间表达

```
dispatch          last_incomplete       Task 完成（真实，不可读）   ended(observed)   persisted(写标)   Flush 返回
   |                    |                          |                      |                |              |
   t0                   t1                        [t1, t2]                t2              t3             t4
                                                        ^ 真实完成落在 (last_incomplete_ms, ended_ms]
```

| 字段 | 含义 | 在行内？ |
|---|---|---|
| `dispatched_ms` | 发出前记录 | 是 |
| `last_incomplete_ms` | 最后一次看到客户端 Task **仍未完成** | 是 |
| `task_completed_observed_ms` / `ended_ms` | 第一次看到 Task 完成（轮询粒度 3ms） | 是 |
| `persisted_ms` | 写标：序列化前 | 是 |
| `flush_returned_ms` | `Writer.Flush()` + `Stream.Flush(true)` 返回 | **否**（不能写进它刚变持久的那一行，另列在运行结果） |

预算按夹逼给：`flush_returned_ms - last_incomplete_ms ≤ 150ms`，并额外用服务端/listener 的真实写完时刻与独立观察者首见时刻交叉验证。
