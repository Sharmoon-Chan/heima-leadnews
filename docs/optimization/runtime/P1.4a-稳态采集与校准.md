## 1. 采集器的数据流

```
计划文件(冻结)            采集循环(单进程)                     三份证据
plan-<rate>-<kind>.json   到期 slot -> SendAsync(不 await)      responses.jsonl  每响应一行(+正文base64)
  slot_index               在途满? -> 记 dropped(不再排队)      resources.csv    每秒 CPU/内存/线程
  planned_offset_ms        完成?  -> 立即写一行 + Flush()       events/<tag>.log 服务端逐请求事件
  article_id               Close() 再刷尾 + fsync
```

关键点：

- **定速**是 `slot.planned_offset_ms = round(i*1000/rate)`；不是「睡够间隔」，因此实际发起时刻带 `schedule_lag_ms`（本卡中位 4–9ms）。
- **观测分辨率**：Windows 上 `Thread.Sleep(1)` 实际是 **15.6ms** 定时器节拍。第一版采集器用它做轮询，导致所有 `elapsed_ms` 聚在 15/16ms（那是采集器的睡眠量子，不是服务端延迟）。修正为「有在途请求时最多忙等 2ms，空载才 Sleep」，代价是采集进程 CPU 上升（本卡归一化峰值 7.7–12.9%，实测记录在 `resources.csv`）。**修正前的数据只作为失败原件保留，不再引用。**
- **落盘策略**：每行 `WriteLine + Writer.Flush()` 后其他进程即可读；`Stream.Flush(true)`（FlushFileBuffers）每 ≤50 条或 ≤200ms 一次并计数（`ledger_fsync_count`）。因此「已 Flush 的前缀」可被中断验证，但**不宣称逐条 fsync**。
- **超时**用每请求的 `CancellationTokenSource.CancelAfter(5000)`（离线用 500ms 证明真的会触发并记 `timeout`），不是靠 Http 客户端总超时。

## 2. 判定口径（一条响应怎么算正确）

```
http == 200
code == 200                       # 200 外壳里装 503 也算失败
raw_text 中 "id":"<期望ID>" 出现   # 字符串 ID 必须在原始字节里成立（数值 ID 解析后无法区分）
article.views/likes/comment/collection == 冻结真值
sha256(data.content 的 UTF-8 字节) == 冻结真值的 content SHA256
```

任一不满足给具体 verdict：`http_status | business_code | invalid_json | wrong_id | wrong_field | wrong_content | transport | timeout`。传输失败只写 `body_unavailable`，**不写 body/bytes**。

真值来自 `SELECT ... SHA2(content,256), LENGTH(content)` 的**直接 SQL 读**。注意两个坑（都在本卡踩过）：`HEX(SHA2(...))` 会**双重编码**；`SHA2()` 本身已经返回小写 hex，不需要再 `LOWER(HEX())`。

## 3. 服务端归属

探针事件按 `X-P1-Request-Id` 分组，一条请求可读出：

| 事件 | 含义 |
|---|---|
| `cache.read hit=true` | 缓存命中（B 组） |
| `cache.read hit=false` + `lock.*` | 未命中并争锁（B 组冷读） |
| `rebuild.begin writeCache=false`（无 `cache.read`） | A 组直查路径 |
| `db.enter` | 一次 DAO 调用（= `articleDetailSnapshotReader.load`，内部两条 SELECT） |
| `db.snapshot.end found=true` | 快照命中文章 |

**DAO 与物理 SQL 分开**：本卡只保留 DAO 证据（A 组 1 次/请求、B 组 0 次），**没有开启 MySQL general log**，所以不报「SQL 条数」。命中/回源是**逐请求归属**后的计数，不是全局 INFO 差。

## 6. 已知边界

- 单机单实例、串行客户端；「5/20/50 req/s」是**实验安排**，不是被测系统的容量。
- 只测存在文章读；空值、随机不存在、写入、混合流量、故障恢复、容量搜索**未测**。
- 连接池指标未接 Actuator/harness → 记 unavailable；JVM 堆/GC 用 `jstat -gc 1000`（`resources/jstat-*.txt`）。
- 采集器是单进程 PowerShell：50/s 时忙等占约 13% 单核；若下一卡要提高速率，应先把采样预算与忙等策略重新冻结，并**新 run_id** 重跑对应档。
- 覆盖预热（1 req/s × 100 ID，A/B 各一遍）**单列**，不进入采样统计。

| 整型 / Decimal | 原有精确路径（Decimal 本身无损，范围判断在 `[long]` 转换之前） |

| 越界/不可精确表示 | `out_of_range`（含 `1e30`、Int64 边界 double），明确失败而不是变值 |

`200.0`/`1.0` 这类**恰好整数**仍被接受，并在 `assessment_notes` 写明"等于该整数"；`200.00000000000003`、`1.0000000000000002`、`0.9999999999999999` 一律 `not_an_integer`。

### 汇总（`p14a-summarize.ps1`）

| 规则 | 实现 |
|---|---|
| 单一人群 | `correct`/`correct_latency_samples`/`verdicts`/`failures`/`timeouts`/`window`/`validated_tiers` 同源；`stored_flags` 与 `segment_validity` 只作对照 |
| 人口一致性 | `correct != correct_latency_samples` 直接报 problem |
| 完整 URL | `collect-result.base` + 计划 path 精确比较；`url_used_a_different_base_not_just_a_path` 单列；`base` 缺失报 problem |
| 计划 hash | 缺失/空即 problem |
| 服务端身份 | joined 请求必须有匹配的 `runId` 与 `articleId`；`server_run_id_missing`/`server_article_id_missing` 计入 problem |
| 反向事件 | 只与 response request_id 集合比对；`dropped_requests_with_server_events` 单列并拒绝 |
| 档位有效性 | 由每段重算 problem 数决定，`segment_validity` 附自报值 |
