## 2. 时间口径

| 名字 | 含义 |
|---|---|
| `dispatch_mono_ms` | 请求即将 `SendAsync` 的单调时刻（在测量辅助里取） |
| `body_ready_mono_ms` | **完整**客户端正文进入内存的时刻（在请求自己的完成续体里取；`ResponseContentRead` 保证不完整就不会有） |
| `observe_mono_ms` | 主循环第一次看到 task 完成的时刻 |
| `ledger_written_mono_ms` | 该行写入之前的时刻；flush 完成时刻无法写进它自己那一行，故 `flush_lag_ms` 单独聚合 |
| `body_latency_ms` | `body_ready - dispatch`（**正式候选延迟**） |
| `observe_lag_ms` | `observe - body_ready` |
| `persist_lag_ms` | `ledger_written - observe` |
| `elapsed_ms`（旧） | `ended_ms - dispatched_ms`，即「派发 → 循环观察」，**旧口径，不回填，永远偏高** |

- 全部来自 `Stopwatch.GetTimestamp()/Frequency`，同一机器级单调轴；整轮时长两条路径互校（实测差 0.3ms）。
- `body_ready` **不是**服务端耗时、**不是** TCP 最后一字节：它包含客户端完成续体与线程池调度。任何引用都必须这样写。
- 没有完整正文（timeout / 传输失败）时 `body_ready_mono_ms=null`，并带 `body_ready_missing_reason`；不补造 bytes/hash。

## 3. 资源观察

- 观察者是**独立进程**，自己的 PID；1s 周期；写 `runs/<runId>/observer/resources.csv` 与 `observer-summary.json`（write-once）。
- 摘要含：`samples`、`gaps.max_ms`、`gaps.over_interval_ms`、`sample_cost_ms.max/mean`、`pids_not_found`、`private_control`。
- 就绪标记在**首个采样完成之后**才写，使进程启动/JIT 不落入测量窗口。
- 采集器的 dispatch/reap 循环**没有**任何资源采样或资源写盘代码；观察者慢/停顿只体现在它自己的 cost/gap 上。
- 归属：`observer_pid / collector_pid / target_pid / idle_pid` 全部显式记录，`pid_identity_matches` 不通过则该 run 失败；不取「最近的 java」。

| 项目 | 门槛 |

## 6. 复跑注意

1. **不要用 `-File` 传 `[int[]]` 数组**（`-Rates 5,20` 会被绑成一个值）。计划生成要么进程内调用
   `& .\benchmarks\env\p14a-plan.ps1 -Rates 5,20 -WarmupSeconds 10 -SampleSeconds 20`，要么另加 CSV 参数。
2. 每个 `p14b-collect` run 都是**新进程**，因此会在派发路径上重新付一次 JIT/编译成本；`dispatch_lag_diagnostic.after_skip`
   只作诊断，**不参与门槛**（门槛判整轮）。
3. 子进程一律重定向到文件，不要用管道捕获（孙进程 JVM 会占住管道）；`Start-Process` 的 `ExitCode` 可能读不到，
   以 `run-status.json` / `recompute` 的摘要文件为准。
4. 主循环忙等 2ms 是有意的（`Thread.Sleep(1)` 在 Windows 上是 15.6ms 节拍）；不要改成 `Sleep(1)`。
5. 观察者、端点、实例都必须由本卡自己的入口启停；不要动其他项目的 java。

## 9. 第8节补修后的生效口径（2026-11-06）

根 `20261105-P1.4b-S8FIX-run-r01`。私有验证 106/106（`b6.*` 13 项），但**功能通过不等于测量质量通过**。

### 9.1 正文窗口按正文戳，不按观察戳

`window_body` 以 `body_ready_mono_ms`（或其冻结偏移）对 `plan.seconds` 判窗；`ended_ms` 的旧窗口 `completed_in_window/after` 只作**单列对照**。二者可以**合法不一致**：负责人边界例（正文 2/0 vs 观察 1/1）本轮已用 `b6.body_window_uses_the_body_ready_stamp` 复现并固定。缺戳/负延迟/乱序三类 `stamp_defect` 一律计入 `body_latency_population_consistent`，不静默丢弃。

### 9.2 P1.4b 测量 verdict 与 P1.4a 业务 verdict 是两个入口

`p14b-summarize.ps1` 只判测量合同（正文窗口、四戳、质量门槛、按 rate/pair/group 全量保留、`budget` 按 planned/offered）。旧 1000 条**没有**新戳，只能 `-Mode legacy`：`legacy_only_records=1000`、`validated_tiers` 为空，**禁止**静默回落到 0 或旧数字；业务结论仍由 `p14a-summarize.ps1` 给出（exit 0 / tiers 5,20 / 100-100-400-400）。

### 9.3 质量门槛是准入，不是报告项

`inputs/private-measurement-gate.json` 由私有套件按实测写出；`p14b-calibrate.ps1` **先读它再建目录**：缺失或 `passed=false` → `exit 2 / REFUSED_STAGE=measurement-gate`。因此「把某个 gate 字段写成 true」不再能让业务段继续执行。2ms 的 observer on/off 正文 P95 差判定也从功能断言移入该 gate。

### 9.4 观察者停顿必须与采集窗口真实相交

`-TestPauseAfterReadyMs` 的停顿门是 `readyWritten && (now-ready)>=AfterReady && (now-start)>=AfterMs`，且 `ready` 在**首个采样完成后**才写（否则停顿会被伪造成「在窗口内」）。`pause_interval` 与采集窗口的交集被显式断言；另有 600000ms 门的对照证明该断言**不空转**（`pause_applied=false`）。采样成本包含停顿，下一次间隔从 `after+interval` 起算。

### 9.5 每个真实写入路径都要证明归属

`P14bPaths.ps1`：`..` **先折叠**、结果必须落在**本活动根**内，**非祖先的其他实验根一律拒绝**（父根拒绝不能代替实际输出路径保护）。observer / collect / capture 的每个写入参数都过这一关，且拒绝发生在**创建文件之前**。

### 9.6 身份要到嵌套值，并哈希实际产物

`capture-p14b-baseline.ps1` 用递归+类型标记的 canonical（`-Xmx512m` 与 `-Xmx513m` 必须不同 hash），`-Phase start|final` + `-VerifyAgainst` 分阶段冻结与校验；程序集记录**distinct hash 集合**（每 run 一份副本，路径列举会随 run 数变化），并且 `Assembly.LoadFile` 加载的就是被哈希的那个 `.dll`。

### 9.7 当前仍失败的一项

派发调度延迟门槛（p95≤5 / p99≤10 / max≤25ms）在 5 req/s **仍未达成**；正文 p95 17.864（A）/ 7.818ms（B）与 60ms 候选无关地通过。失败**只**来自三个 dispatch 门槛。原因仍是**待隔离假设**（见 §8）——`Thread.Sleep(1)` 15.6ms 节拍、新进程/JIT、请求构建、逐记录 JSON/Flush 都是候选，本卡不隔离也不改留存。
